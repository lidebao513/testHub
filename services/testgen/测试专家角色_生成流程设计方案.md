# 测试专家角色 · 生成流程改造设计方案

> 适用范围：testgen-service（URL 通道 + 代码通道）。
> 目标：在生成链路引入"软件测试专家"角色，从专家视角审视**页面实际展示 / 代码真实语义**，产出更贴合预期的测试用例。
> 基线事实（来自代码核查，非推测）：
> - `engine/case_gen.py` 第 7 行明示"**确定性为主，不依赖 LLM**"，用例 1:1 由测试点派生 → 用例质量瓶颈在**上游测试点**。
> - LLM 当前只用于 `semantic_enrich`（补测试点）与 `llm_design`（补候选用例，带 `fp_id` 防臆造护栏），均只吃**代码事实**，不吃渲染结果。
> - URL 通道 `runtime_ui._discover_menu_routes` 靠 CSS 类名启发式找菜单（SPA 实战教训见 `runtime_ui.py:22-29`），本 SPA（投研智能体平台）匹配失败 → 路由发现 0 条 → 仅探索落地页 1 页（`outputs/8/summary.json`：`runtime_ui_pages=1 / routes=0 / elements=17`）→ 99 条用例全派生自 1 页。

---

## 一、可行性评估（结论先行）

| 维度 | 结论 | 依据 |
|---|---|---|
| 专家视角提升"用例相关性/业务流覆盖" | ✅ 高可行、高价值 | 规则引擎是"元素组合式"，天生缺**用户旅程 / 业务风险 / 状态迁移**视角；LLM 多模态读页面可补。 |
| 专家角色修复"覆盖不全（只到 1 页）" | ⚠️ 不能单独解决 | 覆盖不全的根因是**探索器没遍历菜单**，不是用例生成逻辑差。专家若只盯 1 页，只是把 1 页生成得更聪明，仍漏掉其余模块。 |
| 专家读页面反推菜单（治本） | ✅ 高可行 | 规则选择器失败处，LLM 读截图/DOM 能直接列出菜单项 → 回灌 `_discover_menu_routes` 点击遍历。这是覆盖缺口的**唯一低成本治本路径**。 |
| 复用现有 LLM 基建 | ✅ 可行 | `semantic_enrich.LLMClient`（OpenAI 兼容，DeepSeek/Qwen）可直接复用；仅需扩展多模态输入与系统提示。 |
| 风险可控（不臆造/不静默） | ✅ 可行 | 现有 `llm_design` 的 `fp_id` 护栏 + `F10a/F10b` 不静默原则可直接继承。 |

**一句话可行性结论**：方案**可行且值得做**，但必须分两条腿走路——
1. **先治本（Phase 0）**：用专家读页面**反推菜单/路由**，把探索从 1 页扩到全站；
2. **再提质（Phase 1/2）**：专家在每页/每段代码上产出**旅程级 / 风险级**测试点，替代纯元素组合。

只做"专家生成用例"不做"专家驱动探索"，等于重复 99 条只覆盖 1 页的错误。

---

## 二、总体架构：专家角色嵌入两通道

```
【现状】代码 → fp_extract → tp_expand(规则) → [llm_design(代码事实)] → case_gen(确定性)
【现状】URL  → runtime_ui(探索1页) → to_functional_points → tp_expand(规则) → case_gen

【目标】代码 → fp_extract → tp_expand(规则) → expert_code(读代码·生成+审查) → case_gen
【目标】URL  → runtime_ui ──┬─ expert_page.propose_routes(读页面反推菜单) → 点击遍历↺
                            └─ expert_page.review_page(逐页读渲染) → 专家测试点
              → to_functional_points + 专家FP → tp_expand(规则) → case_gen
```

**关键设计原则（继承现有红线）**
- 专家产出**只增不加**（additive）：绝不删减规则用例，规则用例是稳定基线（内容指纹 id，可溯源）。
- **不臆造护栏**：专家测试点的 `area/selector/route` 必须真实存在于"已抓取页面 / 已发现路由 / 已捕获 XHR"，否则进 `rejected` 并公示。
- **不静默**：专家未启用或模型缺失 → 返回空 added + `notes` 明示"未新增任何专家用例"（沿用 `F10b`）。
- **可判定优先**：专家用例尽量带真实 `selector`（供 UI 执行器断言），纯描述性风险用例标 `unverified` + `review_status=pending`（沿用 `_BEST_EFFORT_DIMS` 机制）。
- 生成-only 红线不变：`/api/v1/generate` 仍不触发执行。

## 三、URL 通道设计：Page Test Expert（页面测试专家）

### 3.1 输入：页面抓取快照 `PageCapture`
复用 `runtime_ui` 已采集的字段，新增可选截图（多模态）：

```python
@dataclass
class PageCapture:
    url: str
    path: str
    title: str
    screenshot_b64: str | None = None   # 多模态输入（需视觉模型）
    dom_text: str = ""                   # 页面文本/DOM 结构（文本模型兜底）
    elements: list[dict] = field(default_factory=list)   # [{selector,kind,text,visible}]
    console_errors: list[str] = field(default_factory=list)
    xhr_list: list[dict] = field(default_factory=list)    # [{method,url}]（XHR 拦截）
    auth_mode: str = "required"
    discovered_routes: list[str] = field(default_factory=list)
```

### 3.2 两个职责（核心）
**(A) `propose_routes(capture) -> list[str]` — 治本**
读截图/DOM，**列出规则选择器没抓到的菜单/导航项文本**，回灌 `_discover_menu_routes`：
```python
def _discover_menu_routes(page, ctx, opts, result):
    labels = _nav_labels(page) or _expert_propose_labels(page)  # ← 规则空了就问专家
    ...
```
这正是修复 `routes=0` 的机制——专家不依赖 CSS 类名，直接"看"侧边栏文字。

**(B) `review_page(capture, existing_tps) -> ExpertResult` — 提质**
对单页产出**旅程级/风险级**测试点（规则引擎缺失的视角）：
- 用户主流程（如 登录→新建会话→输入→发送→查历史 作为一条 E2E 旅程）；
- 业务规则组合（权限矩阵、状态机迁移、依赖顺序）；
- 真实边界（页面临界值、列表空态/超长、移动视口）；
- 安全直觉（未授权直达、输入注入、越权读他人数据）。

### 3.3 模块骨架
```python
# engine/expert_page.py
@dataclass
class PageExpertOptions:
    enabled: bool = False
    provider: str = "deepseek"
    base_url: str = ""
    api_key: str = ""
    model: str = ""            # 视觉模型（如支持）或文本模型
    use_vision: bool = False   # True=带截图；False=仅 DOM 文本（deepseek-chat 为文本模型时）
    timeout: int = 60
    max_tps_per_page: int = 8

_SYSTEM_PROMPT = (
    "你是资深软件测试专家，专注 UI/端到端测试。基于页面**实际渲染**（截图+DOM+交互元素+网络请求），"
    "从测试专家视角设计测试点。\n硬性约束：\n"
    "1) 只基于真实存在的元素/路由/请求设计，不得臆造 selector 或路由；\n"
    "2) 优先产出规则引擎缺失的『用户旅程 / 业务风险 / 状态迁移』类用例；\n"
    "3) 输出 JSON 数组，字段："
    '{"area":"选择器或路由","category":"正常|异常|安全|边界",'
    '"dimension":"子维度","title":"标题","expect":"预期","priority":"P1|P2",'
    '"verify_layer":"UI|接口","rationale":"为什么这条有价值"}\n'
    + _INJECTION_GUARD
)
```
护栏（沿用 `llm_design._validate_candidate`）：`area` 必须是 `elements` 里的 `selector` 或 `discovered_routes`/`xhr_list` 里的真实项，否则拒绝。

### 3.4 契约变更（Additive，向后兼容）
`TestPoint`/`CaseSpec` 增加 `origin` 字段（旧消费方忽略）：
```python
# core/contracts.py 新增取值
ORIGIN_RULE = "rule"            # 规则引擎
ORIGIN_LLM_ENRICH = "llm_enrich"
ORIGIN_EXPERT_PAGE = "expert_page"
ORIGIN_EXPERT_CODE = "expert_code"
ORIGIN_LLM_DESIGN = "llm_design"
```
报告据此展示"专家增补覆盖增量"。

## 四、代码通道设计：Code Test Expert（代码测试专家）

### 4.1 现状与缺口
代码通道现有 `semantic_enrich`（补测试点）+ `llm_design`（补用例）。缺口：
- 只吃"功能点列表"，不吃**函数体/上下文**，难产出"这个函数有状态机但没测状态迁移"这类洞察；
- 没有"**审查**"视角——用户说"生成内容与预期偏差"，本质是缺一个**对照预期审计规则产出**的角色。

### 4.2 模块骨架
```python
# engine/expert_code.py（演进自 llm_design + semantic_enrich）
def review_code(fps, tps, prd, options,
                mode: str = "both"   # generate | review | both
                ) -> ExpertCodeResult:
    ...
# generate：比 llm_design 多吃函数体+调用关系，仍守 fp_id 护栏
# review  ：专家审计规则测试点，输出 coverage_gaps（"缺 X 场景"）+ 可选补点
```
- **generate 模式**：输入增强为"功能点 + 其源码上下文（AST 节点/签名/调用函数）+ 已有测试点"，产出 `origin=expert_code` 测试点；守 `fp_id` 真实护栏。
- **review 模式（直接回应"偏差"诉求）**：专家读规则产出的测试点，对照函数语义给出**覆盖缺口清单**（如"未测并发写""未测空输入回退""越权只测了读没测写"），并可一键补点。这份"缺口报告"本身就能解释为什么生成内容与预期不同。

### 4.3 与现有模块关系
- 不推翻 `tp_expand`（规则展开仍是稳定基线、内容指纹可溯源）；
- `expert_code` 在 `tp_expand` 之后叠加（generate）或在之前审查（review）；
- 最终取代 `llm_design` 的显式调用（统一为专家角色），`semantic_enrich` 保留为"轻量规则增强"可选项。

## 五、具体落地方案（分阶段）

### Phase 0 — 治本：专家驱动菜单/路由发现（最高优先）
- 改 `runtime_ui._discover_menu_routes`：规则 `_nav_labels` 为空时调 `expert_page.propose_routes`（读 DOM/截图列菜单项文本）→ 点击遍历。
- 复用现有 `LLMClient`；新增 `propose_routes` 的 JSON 输出解析 + 点击回灌。
- **验收**：对 `101.43.2.52:9001` 重跑，路由数从 0 → 真实菜单数（预期 10+），`runtime_ui_pages` 跳升。
- 风险：视觉模型若不可用 → 退化到 DOM 文本（仍比 CSS 选择器稳）。

### Phase 1 — URL 通道：Page Test Expert 提质
- 新增 `engine/expert_page.py`（`PageCapture` / `PageExpertOptions` / `propose_routes` / `review_page` / 护栏）。
- `pipeline.py` 在 `runtime_ui` 产出 `pages` 后，逐页调 `review_page`，专家测试点并入 `tp_expand` 之前的集合。
- 配置：`settings.expert_enabled` / `expert_vision`；CLI `--expert`（URL 通道开关）；凭证复用 `llm_*`。

### Phase 2 — 代码通道：Code Test Expert
- 新增 `engine/expert_code.py`（`review_code` 含 generate/review 两模式）。
- `pipeline.py` 用 `expert_code(mode=settings.expert_code_mode)` 替代 `llm_design` 调用；保留 `--expert-code` 开关。
- `review` 模式产出 `coverage_gaps` 进报告。

### Phase 3 — 契约/报告/门禁
- `core/contracts.py` 加 `origin` 字段（Additive）。
- 报告新增"专家增补覆盖"段（按 `origin` 汇总增量 + 覆盖缺口清单）。
- 八环门禁补 `expert` 相关检查（专家用例 `origin` 必填、护栏拒绝率阈值告警）。

### Phase 4（可选演进）— 自主探索 Agent
- 把专家升级为 ReAct Agent：自带浏览器工具，自主"看页面→决定测什么→执行探针→补点"，实现用户设想的"专家审视页面自主生成"。
- 代价：延迟/成本显著上升，需限流与人工抽检；建议 P1–P3 验证价值后再上。

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| 多模态：deepseek-chat 非视觉模型 | `use_vision=False` 走 DOM 文本；视觉模型单独配置 `model` |
| 非确定性（专家输出每次不同） | 专家用例标 `unverified`+`review_status=pending`；规则用例仍是稳定基线 |
| 臆造 selector/路由 | 护栏：`area` 必须命中已抓取元素/路由/XHR，否则 `rejected` 并公示 |
| 成本/延迟（多页×多调用） | 每页一次批量；`max_tps_per_page` 封顶；可只对有菜单页启用 |
| 覆盖仍不全（专家不驱动探索） | 强制 Phase 0 先落地，否则 URL 专家只看到 1 页 |
| 静默失效 | 沿用 `F10b`：未启用/缺模型 → 空 added + notes |

---

## 七、预期收益（对照本次 99 条问题）

1. **覆盖**：Phase 0 后探索从 1 页 → 全站菜单页（预期 FP/用例数显著上升，且跨模块）。
2. **相关性**：专家旅程/风险测试点填补规则"元素组合"盲区，更贴近"测试专家预期"。
3. **可解释**：`review` 模式直接产出"覆盖缺口报告"，回答"为什么生成内容和预期不一样"。
4. **可控**：additive + 护栏 + 不静默，专家出错不污染规则基线、不粉饰。

## 八、需要你拍板的点

1. **视觉模型**：是否提供视觉模型 endpoint（截图输入），还是先用 DOM 文本（deepseek-chat）起步？
2. **优先级**：先落地 Phase 0（治本·导航发现）还是直接搭 Phase 1 专家模块？
3. **代码通道**：是否同步做 `review` 模式（覆盖缺口报告），还是先只做 generate？
4. **专家强度**：单轮 LLM（低成本）还是 Phase 4 自主 Agent（高成本高自主）？
