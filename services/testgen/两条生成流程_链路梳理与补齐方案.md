## 一、链路总览

### 1.1 完整链路（现状）

```
                ┌──────────── 流程一：基于代码 ────────────┐
  [取码]        │  外部技能 / 脚本 → work/targets/<repo>   │   ← ⚠️ 服务外
      ↓         └──────────────────────────────────────────┘
  stage_register   pipeline.py:121   项目登记（upsert_project）
  stage_scan       pipeline.py:133   扫描源码 → SourceFile 索引      scan.py
  stage_extract    pipeline.py:146   提取功能点 FP（api/page/component/business） fp_extract.py
      ↓                              ┌── M3.4：运行时 UI 功能点并入（按 (ftype,name) 运行时优先）
      │                              │
                ┌──────────── 流程二：基于 URL + 账号密码 ──────────┐
                │  stage_runtime_ui  pipeline.py:299  Playwright 登录 │
                │  → 菜单点击发现路由 → 抓真实可交互元素              │
                │  to_functional_points  runtime_ui.py:918           │
                └───────────────────────────────────────────────────┘
  stage_tag        pipeline.py:188   diff 打标：全量 / 更新          diff_tag.py
  stage_test_points pipeline.py:208  功能点 → 测试点（正常/异常/安全/边界） tp_expand.py
  stage_enrich     pipeline.py:227   语义增强（LLM，可选，默认关）    semantic_enrich.py
  stage_prd_ingest pipeline.py:247   PRD/OpenAPI → 业务规则测试点（P2，默认关） prd_ingest.py
  stage_cases      pipeline.py:378   测试点 → 用例（1:1，八要素）     case_gen.py
  stage_llm_design pipeline.py:277   LLM 用例设计                    ⛔ 桩
  stage_execute    pipeline.py:361   用例执行                        ⛔ 桩
  stage_persist    pipeline.py:421   幂等落库（replace + reconcile）  store.py
  OutputWriter     output/writer.py  产物：test_points.json / test_cases.json /
                                     TEST_CASES.md / summary.json
```

### 1.2 一句话结论

| 流程 | 端到端可用性 | 说明 |
|---|---|---|
| **① 基于代码** | ✅ **可用** | 从「已有代码目录」到「用例产物」全链路真实跑通（research-agent 实测功能点 768 / 用例 1200） |
| **② 基于 URL + 账号密码** | ❌ **不可用** | 只做到「登录 + 发现 UI + 输出功能点清单」；**无法独立产出测试点与用例** |

**根因（最关键的一条）**：`run_pipeline` 在入口处强制要求代码目录存在——
`pipeline.py:462-464`：

```python
local = Path(opts.local_path)
if not local.is_dir():
    raise EngineError(f"被测目录不存在：{local}")
```

且 `stage_scan`（`pipeline.py:469`）**无条件执行**。因此流程二目前是**寄生在流程一上的旁路增强**：
必须有代码目录、必须代码扫描成功，运行时 UI 才发现得了；没有代码目录则整个 pipeline 直接抛错。
独立工具 `tools/run_runtime_ui.py` 的 `_summarize()`（`tools/run_runtime_ui.py:79-113`）
**只输出功能点，不含测试点与用例**——即流程二当前**没有自己的「生成用例」出口**。

## 六、实施建议

### 阶段一：让两条流程对等（P0，目标=「两条路都能出用例」）

**A1 · 流程二补入口（无代码模式）**

1. **放开代码目录硬依赖**：`run_pipeline` 入口改为「至少要有一种输入来源」——
   `local_path` 有值 → 走代码；`local_path` 为空但运行时 UI 开启 → 走 URL 模式；
   两者都没有 → `EngineError`（**保留快速失败**，只是不再强制代码）。
   `stage_scan` / `stage_extract` 在 URL 模式下跳过，`result.functional_points` 起点为空列表。
2. **请求级凭证入参**（红线不变）：
   - `RuntimeUiOptions` 已承载 `login_user/login_password/login_otp`，只需让 `PipelineOptions`
     能携带一份运行时配置覆盖（**仅内存传递**）；
   - 凭证**仍不得**进入 `public_dict()`、日志、产物 JSON、用例文本与数据库；
   - 产物与 `summary.json` 中只允许出现 `runtime_login_configured: true` 这类布尔。
3. **入口参数**：
   - CLI：`pipeline` 增 `--url/--login-url/--user/--password/--otp/--route（可重复）/--no-menu`；
     与 `--path` 二选一或同时给（同时给 = 代码 + URL 双源合并，即现在的行为）。
   - HTTP：`PipelineRequest` 增同名字段（`password` 用 `SecretStr` 语义，响应中绝不回显）。
4. **目标形态**（贴合「统一智能输入框」习惯）：允许一次提交「URL + 账号 + 密码 + 动态口令 + 权限范围」，
   内部按有无代码自动分流。

**A2 · 运行时上下文落进用例正文**

1. `PipelineResult` 增一个**只读**的运行时上下文视图（如
   `runtime_context: dict[route, {title, elements, console_errors}]`），由 `stage_runtime_ui` 填充。
2. `case_gen.build_doc_steps` 增可选参数 `runtime: RuntimeContext | None`：
   - UI 层用例的「准备/执行」改为**具体化**：
     例 `打开页面：/pc/tasks（福享任务）` → `定位交互点：button「新建任务」（selector: …）`；
   - 「断言」带上该页真实采集到的**控制台错误基线**（`0 条` vs 实测 N 条）；
   - 无运行时上下文时**原样回落模板**（保证流程一零回归）。
3. **契约只增不破**：`doc_steps` 仍是 `list[dict]`，仅新增字段（如 `selector` / `runtime_source`）。

**A3 · 执行器接口层最小实现**

1. `executor.execute_case(case, options)` 按 `steps[0].layer` 分派：
   - `interface` → `http_probe`：`requests` 发 `steps[0].method + path`，按 `expect` 与维度判定
     （正常→2xx；异常→4xx/5xx 且非 5xx 崩溃；安全→401/403）；
   - `ui` → **本期返回 `SKIPPED` 并注明「UI 执行待 C2」**（诚实跳过，不假通过）。
2. `stage_execute` 真实调用并把结果写入 `ExecutionResult`；落库侧把结果回填 `cases.last_result`（表已存在）。
3. **无 `base_url` 时整体 `SKIPPED`**，绝不用「探活成功」冒充「用例通过」。

### 阶段二：消除陷阱与提高适应性（P1）

- **B1**：`LLM_DESIGN_ENABLED=on` / `EXECUTOR_ENABLED=on` 而能力未就绪时，
  在 `result.errors` 或 `result.notes` **明确写出**，杜绝静默。
- **B2**：`_build_diff_context` 对「明确指定了 `base/target` 但不可解析」→ `EngineError`；
  仅当**未指定**时才降级全量。
- **B3**：`requests` 降级路径落地，并把 `degraded=True` 如实回传。
- **B4**：HTTP 契约补齐 URL 流程字段，为服务化（testhub / 流水线）铺路。

### 阶段三：提升用例质量（P2/P3）

- **C2** UI 执行（Playwright）、**C3** LLM 用例设计（带「只许基于已提取事实、不许编接口、生成即 pending」两条护栏）、
  **C4** 安全深化、**C5** 调用图吞并与 UI 测试点细化。

### 验收口径（每阶段可独立验收）

| 阶段 | 验收方式 |
|---|---|
| 阶段一 | ① 不带 `--path`、只给 `--url/--user/--password` 能产出 `test_cases.json` 与 `TEST_CASES.md`，且用例数 > 0；② 该用例的 `doc_steps` 中出现**真实路由与真实元素**（如 `/pc/tasks`、具体按钮文案）；③ `EXECUTOR_ENABLED=on` + 可达接口时能给出 `passed/failed` 判定；④ 全量回归 + 八环门禁通过；⑤ **凭证扫描干净**（仓库内零账号/密码/动态口令痕迹） |
