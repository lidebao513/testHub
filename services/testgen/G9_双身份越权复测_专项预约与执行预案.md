## 一、为什么必须「专项预约」而非自动执行

跨租户越权（G-9）用例在**生成期**只能诚实跳过：判定越权是否成立，必须用「**两个真实身份 + 他人 resource_id**」重放，单令牌无法构造。

真实复测有三条硬约束，决定了它不能像普通用例那样随流水线自动跑：

1. **需要第二个真实身份凭证**：平台不持有「他人」账号密码，必须由调用方显式提供（`--other-user` / `--other-password`）。只给属主一方时，通道会**诚实降级为 `skipped`**，绝不伪造 `PASS`。
2. **对数据共享环境有真实泄露风险**：`ft.cntaiping.com` 是数据共享环境，复测会用属主身份取真实 `resource_id`，再用他人身份去读/写该 id。一旦隔离失效，他人身份会读到属主数据 = **真实数据泄露**。因此**绝对禁止对生产环境跑**，必须用在隔离测试租户。
3. **需专项审批 + 隔离账号**：跨租户越权复测属于高危操作，须走审批（记录 approver + 工单号），并在专属隔离账号下进行。

结论：把它列为「月度预约项」——每月提醒一次「环境/账号/审批是否就绪」，就绪后由人工手动触发，结果如实落盘，**绝不编造通过**。

## 二、通道能力（已实现，代码位置）

- 复测模块：`engine/tenant_retest.py`
  - `is_tenant_case(case)`：识别 `安全-越权读他人数据` / `安全-越权写他人数据`（`TENANT_READ` / `TENANT_WRITE`）维度用例。

- 测试：`tests/test_g10_g11_g9.py`（用桩会话验证双身份路径，不触真实网络）。

## 三、红线清单（执行前逐条确认）

1. **绝不触生产 `ft.cntaiping.com`**：只跑在专属**隔离测试租户**（两个账号同应用、不同租户/数据域，数据均为非敏感测试数据）。
2. **不发写操作到属主数据本身**：他人重放只读 / 越权写（由用例 method 决定），均属「探测越权」；属主侧仅做一次 `GET` 取 `resource_id`。
3. **凭证不入库、不日志**：账号密码只经进程环境变量 / CLI 参数注入，绝不写入 DB、日志、产物文件（与 runtime_ui / executor 同一红线）。
4. **失败即失败，绝不粉饰**：他人身份若读到属主数据 / 越权写成功 → 记为高危 `fail` 并明确标注，立即停手上报，**不得掩盖**。

## 五、精确执行命令（复制即用）

在 `work/testgen-service/` 目录下，用项目 venv 运行（Windows Git Bash / PowerShell 均可）：

```bash
cd work/testgen-service

./venv/Scripts/python.exe -m cli.main tenant-retest \
  --project <PROJECT_ID> \
  --url https://<隔离测试环境>/api \
  --owner-user <属主账号_隔离> \
  --owner-password <属主密码_隔离> \
  --other-user <第二身份账号_隔离> \
  --other-password <第二身份密码_隔离> \
  --out output/tenant_retest
```

备选（凭证走环境变量，避免命令行暴露密码）：

```bash
cd work/testgen-service

export RUNTIME_LOGIN_USER=<属主账号_隔离>
export RUNTIME_LOGIN_PASSWORD=<属主密码_隔离>
export RUNTIME_UI_BASE_URL=https://<隔离测试环境>/api

./venv/Scripts/python.exe -m cli.main tenant-retest \
  --project <PROJECT_ID> \
  --other-user <第二身份账号_隔离> \
  --other-password <第二身份密码_隔离> \
  --out output/tenant_retest
```

- 不加 `--out`：结论只打印 JSON 到 stdout。
- 加 `--out`：额外把 `tenant_retest.json` 写到该目录。
- 缺 `--url` 且未设 `RUNTIME_UI_BASE_URL` → 报错退出（码 2）。
- 缺属主身份 → 报错退出（码 2）。
- **缺 `--other-user` / `--other-password` → 不报错，但所有 G-9 用例统一 `skipped`（诚实跳过，非真实结果）**。这是最常见的「跑了等于没跑」陷阱。

## 六、结果判定与处置

`tenant_retest.json`（或 stdout）结构：

```json
{
  "total_tenant_cases": 12,
  "counts": { "pass": 10, "fail": 0, "skipped": 2 },
  "results": [ { "tc_no": "...", "title": "...", "result": "pass|fail|skipped", "status": 403, "resource_id": "...", "reason": "..." } ]
}
```

| result | 含义 | 处置 |
|--------|------|------|
| `pass` | 他人身份被拒（读 401/403/404 且不泄露属主数据；写 401/403/404），隔离有效 | 记录归档，复测通过 |
| `fail` | 他人身份读到属主数据 / 越权写成功 = **高危越权** | **立即停手、上报、开缺陷单修复**；不得掩盖 |
| `skipped` | 无他人凭证 / 属主取不到 resource_id / 用例无 path | 非真实结果，补齐条件后重跑；不得当作通过 |

判定口径（源码 `retest_case`）：
- 读越权：`status ∈ {401,403,404}` **且** 他人响应体不含属主 `resource_id` → `pass`，否则 `fail`。
- 写越权：他人 `PUT/POST/...` 该 `resource_id` 返回 `401/403/404` → `pass`，否则 `fail`。

## 九、常见陷阱

1. **用生产 `ft.cntaiping.com` 跑** → 真实数据泄露，红线违规。只用隔离测试租户。
2. **忘了给 `--other-user`** → 全部 `skipped`，看似跑完实则没验证越权。
3. **用例没落库就跑** → `tenant-retest` 从 `cases` 表取数，`--project` 无用例直接报错退出。先跑一次 `pipeline` 生成 + 落库。
4. **把 `skipped` 当 `pass` 汇报** → `skipped` 是无结论，不是通过；只有显式 `pass` 才算隔离有效。
5. **密码写进日志/产物** → 违反红线 3；用环境变量或 CLI 参数临时注入，跑完即弃。
