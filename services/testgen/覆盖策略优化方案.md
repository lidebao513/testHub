# 测试用例生成 · 覆盖策略优化方案

> 目的：回答三个疑问（业务函数膨胀、别人为何提取更多、给测试地址是否更完善），
> 并给出一个可落地的「三层互补 + UI 优先」方案。

---

## 一、先回答三个问题

### Q1 ·「收窄业务函数 → 功能点」是什么，怎么判断？

**现状（本仓库实测）**：当前提取器把「每一个公开的 Python 函数」都算成一条业务功能点，
导致 **692 条业务功能点**（占全部 1004 条功能点的 69%）。这就是接口层「显得很多」的根源。

**把这 692 条拆开看，构成是：**

| 来源类别 | 估算条数 | 性质 | 处置 |
|---|---|---|---|
| 测试 / 脚手架代码（如 `regression/run.py`、`_fx_test` 测试套件） | ~207 | 根本不是被测功能 | **应直接排除** |
| 配置 / 迁移 / 建表脚本 | ~27 | 非业务能力 | 应排除或降级 |
| 真正的后端能力（`tools/`、`mcp_servers/`、`agents/`、`workspace/skills/` 下的工具/智能体/监控/同步任务） | ~438 | 独立可触发能力 | 应保留 |
| 与 API 路由同文件的辅助函数 | ~54 | 能力已被路由用例覆盖 | 标 supplement 或丢弃 |

**「收窄」= 把"凡是函数都算功能点"收紧为"只保留真正可独立触发的能力"。**

**你（或系统）判断的四步法，从「零歧义」到「需人判」：**

1. **自动排除测试/脚手架/配置迁移（零风险，立刻能做）**
   仅此一项就把业务功能点从 **692 → ~458**，全量功能点 **1004 → ~797**，
   且**真实覆盖一条都不会少**（被排除的本来就不是被测物）。
2. **调用图吞并**：被某条 API 路由直接调用的辅助函数 → 它的能力已被那条路由的用例覆盖
   → 复用我们已有的 `coverage_role` 机制，标成 `supplement` 或直接丢弃（和 UI 优先同一套逻辑）。
3. **显式能力白名单（保留）**：带 `@task / @cron / @subscriber / @worker / @command`，
   或位于 `tools/ agents/ mcp_servers/ workspace/skills/` 的公开函数 → 是明确的独立能力，保留。
4. **LLM 意图分类（可选兜底）**：对仍拿不准的函数，用 DeepSeek 读函数体+docstring，
   判定「是否对用户/外部系统构成独立可触发能力」。

**你可以怎么「判断」**：我导出一份《业务功能点清单（按模块分组 + 来源类别标注）》，
你扫一遍标题即可：标「测试/配置」的直接删，标「工具/智能体/任务」的保留，
拿不准的我走第 4 步用 LLM 判。

### Q2 · 那篇微信文章（DeepSeek Harness）为什么能「提取更多」？

**关键差异**：它不是静态代码分析，而是 **DeepSeek 大模型 + 接口文档（PRD/Word/PDF）** 的「用例设计」。

它的「多」来自两点：
- 对每个**真实接口**，大模型展开 等价类 / 边界值 / 异常场景（3 个接口生成 50+ 用例，约 17 用例/接口）；
- 还能补**隐性业务规则**（文章举例：VIP 用户不受库存上限限制）。

**代价（文章自己承认）**：会「编」不存在的接口、假设错返回字段名、漏掉没写进文档的规则
→ 所以文章反复强调「生成完必须人工过一遍」。

**我们的「少」是另一种少**：我们是**确定性代码提取**（每个真实路由/函数 = 1 功能点），
不臆造、每条都能追溯到代码证据，再用「正常/异常/安全/边界」四类展开测试点。
我们不是少，是「每条都经得起核对」。

**我们可以直接借鉴、且能规避它毛病的两点（我们目前缺的）：**
- 缺「**文档/PRD 作为输入通道**」→ 隐性业务规则目前抓不到（这是文章的核心优势）。
- 用例设计环节可以用 **LLM 增强**（文章全链路最强的一环），但加两条护栏：
  **① 只许基于已提取的真实代码事实、不许编接口；② 生成即 `pending` 人工复核（REVIEW_GATE）**。

### Q3 · 给测试地址 + 账号密码去读页面，会更完善吗？

**会，而且正好补上我们当前最大的 UI 短板。**

静态分析只能「猜」页面（靠 `path=` 声明 / 目录名 / `*Page` 命名），它**看不到**：
- 登录后才出现的**权限菜单 / 路由**；
- **懒加载模块**、由接口数据动态生成的页面；
- 真实**表单字段**、真实**校验提示**、真实**交互流**。

**做法**：用浏览器（Playwright）登录测试环境 → 爬真实渲染的 SPA → 发现真实路由树
（含权限门控页）→ 抓真实页面/组件/表单 → 生成贴合用户实际所见的 UI 测试点。

**重要前提**：我们平台目前的执行器**不跑浏览器**（只有 requests 探活 + 静态断言），
所以这一步需要补 **Playwright 能力**（项目记忆里已标记为已知缺口）。

**它和代码分析是「互补」不是「替代」**：代码分析便宜、全、确定；运行时爬取负责验证/扩展、
抓运行时独有页面。

## 二、更合理的方案：三层互补 + UI 优先

```
        ┌─────────────────────────────────────────────┐
        │          被测系统（代码 + 测试环境）           │
        └─────────────────────────────────────────────┘
           │                │                  │
   ┌───────▼──────┐ ┌───────▼───────┐ ┌───────▼────────┐
   │ 第0层 代码静态 │ │ 第1层 LLM用例 │ │ 第2层 运行时UI  │
   │ 提取(现有·先收窄)│ │ 设计(借文章长处)│ │ 发现(借你给的    │
   │               │ │ +护栏         │ │  测试地址)      │
   │ · 确定性可溯源 │ │ · 等价类/边界/ │ │ · 浏览器登录爬  │
   │ · 零臆造      │ │   异常/业务规则│ │   真实渲染页面  │
   │ · 先排除测试/ │ │ · 锚定真实代码 │ │ · 抓权限门控/   │
   │   配置+吞并   │ │   不许编接口   │ │   动态/表单     │
   │ · 功能点=真实 │ │ · 生成即待复核 │ │ · 补UI层真实面 │
   │   能力        │ │ + 接PRD通道    │ │                │
   └───────┬──────┘ └───────┬───────┘ └───────┬────────┘
           └────────────────┼──────────────────┘
                            ▼
              ┌───────────────────────────────┐
              │   统一策略：UI 优先覆盖        │
              │  UI 层优先生成；接口仅补充      │
              │  UI 够不着的能力(coverage_role)│
              └───────────────────────────────┘
                            ▼
                   ┌──────────────────┐
                   │  测试用例集(交付) │
                   └──────────────────┘
```

- **第0层 代码静态提取（现有，先收窄）**：确定性、可溯源、零臆造。先做 Q1 的
  「自动排除 + 调用图吞并」，让功能点 = 真实能力，数字才可信。
- **第1层 LLM 用例设计（借鉴文章长处，加护栏）**：对每个真实功能点，用 DeepSeek 展开
  等价类/边界/异常/业务规则场景；护栏 = 只基于已提取代码事实、不许编接口、生成即待复核。
  同时开放「上传 PRD/接口文档」通道补隐性规则。
- **第2层 运行时 UI 发现（借你给的测试环境）**：浏览器登录爬真实页面，补权限门控/动态页面，
  让 UI 层真正贴合用户所见。
- **统一策略**：全程套用「UI 优先」——UI 层优先生成，接口仅补充 UI 够不着的能力
  （`coverage_role` 已落地）。

## 三、落地优先级（低风险先上）

| 优先级 | 工作 | 依赖 | 收益 |
|---|---|---|---|
| **P1** | 业务功能点收窄（零歧义排除 + 调用图吞并） | 无，纯代码改动 | 立刻让数字可信，FP 1004→~797，覆盖不减 |
| **P2** | 文档/PRD 输入通道 + LLM 用例设计（护栏版） | 接 DeepSeek（你其他项目已用） | 补隐性业务规则，单接口用例更丰富 |
| **P3** | 运行时浏览器爬取（Playwright 执行器） | 补浏览器能力 + 你的测试地址 | UI 层贴合真实页面，抓权限门控页 |
| 全程 | 策略写入 `qa-test-points` 技能 §十三 | — | 自动沿用、可调 |

## 四、需要你确认 / 提供的

1. **是否先把 P1（收窄）直接落地？** 我建议先做，改动小、立竿见影、不引入新依赖。
2. **测试环境地址 + 账号密码**：用于 P3，也可先用于验证 P1/P2 的接口用例。
3. **PRD / 接口文档**：是否愿意喂给 P2，以补隐性业务规则覆盖。
