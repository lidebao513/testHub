# 生成方式评估：保持当前规则，还是全部转 UI 可执行

- 日期：2026-11-17
- 状态：**仅分析，未改任何实现代码**
- 结论摘要：**不应该"全部转 UI"**。真正的瓶颈不是"层"，是**具体化程度**。UI 用例当前可读但不可操作，接口用例可判定但不可读——两边都差"具体化"这一刀。正确路线是"分层各司其职 + 各自具体化"。

---

## 一、实测方法与原始数据

为了不让结论停留在推测，用真实代码跑了生成链路（不调 LLM，纯规则），样本是本平台自己的前端：

| 项 | 数据 |
|---|---|
| 样本 | `frontend/src`（204 个文件，Vue 3 + Element Plus） |
| 提取结果 | 146 个功能点（145 page + 1 component） |
| 测试点 | 1016 条（145 页面 × 7 维度 + 1 组件 × 1 维度） |
| 用例 | 1016 条，全部 `layer=UI`、`action=ui_probe` |
| 页面路径唯一性 | 145 条 page 功能点里**只有 121 条唯一路径**，38 条重复（`/Dashboard.vue x6`、`/ScheduledTasks.vue x4` 等） |
| 单页面 7 条用例的"执行"步骤 | **唯一文案数 = 1**（7 条全是"访问 /home，等待首屏渲染完成并收集控制台错误"） |

对照后端业务函数侧（此前 project 33/35 实测）：

| 项 | 纯规则版（project 33） | LLM 增强版（project 35） |
|---|---|---|
| 条数 | 4 | 26（规则 4 + LLM 22） |
| 标题 | `get_domain_detail（入参 domain_id、top_n）` | 同左 |
| 预期 | `（入参…；返回 dict[str,Any]）函数被正常调用…` | `top_n=0 应返回空结果`、`top_n=负数 应报参数校验错误` |

## 二、关键发现（4 条）

### 发现 1：可读性不是由"层"决定的，是由"具体化程度"决定的

直觉上"UI 层 = 可读"，实测不成立：

- 当前 UI 用例（1016 条）文案确实人话：`打开页面：/home`、`不白屏`、`有友好提示`。
- 但**它不可操作**：7 个维度里 4 个异常维度（网络中断、错误回显、空状态、错误页）的"执行"步骤与"正常"维度**一模一样**，都是"访问页面等渲染"。没人能照着这条去"制造 5xx"或"造空数据"。
- 反过来，后端函数用例一旦具体化（LLM 版 `top_n=0/负数/极大值`），**即使层级是接口，业务同学也能看懂在测什么**。

一句话：可读性差的根因是"抽象层级太高（只有函数名）"，不是"层级是接口"。

### 发现 2：UI 层用例目前是"页面可达性检查 × 7 种断言"，不是"UI 操作流程"

现状 7 个维度（PAGE）：页面/路由可达、未授权访问、极端视口、网络中断、错误回显、空状态、错误页。

这 7 条**只换断言不换执行**，等于对同一个动作（打开页面）下了 7 个不同判据。真正的 UI 用例应该是"做了什么操作 → 界面怎么变"，例如：

- 现状：`触发 DataFactorySelector.vue 的交互（点击／输入），观察界面响应`
- 应然：`在项目列表页点击『新建项目』→ 弹窗出现 → 名称留空点确定 → 红字提示"名称不能为空"`

后者需要三个当前缺失的东西：**真实元素名、具体操作序列、具体测试数据**。

### 发现 3："全部转 UI"的硬门槛是"能力 → 页面操作映射"，这个映射现在不存在

代码里 `layer_strategy` 默认已是 `ui_first`，但它的语义被人误解了：

- 它做的只是：**某个模块已有 UI 覆盖时，把该模块的接口用例降为 `supplement`（补充）**，`drop_supplement_cases` 默认 False 所以补充用例仍保留。
- 它**不做**"把接口用例改写成 UI 用例"。因为做不到——后端函数/接口没有任何信息能告诉系统"它由哪个页面的哪个按钮触发"。
- `ui_modules` 的粒度是**模块级集合**（哪些模块有 UI），不是**操作级映射**（哪个接口对应哪个按钮）。

所以：**只有①前端产物、②路由/组件、③UI 入口这三样齐全的能力才能生成 UI 用例**。纯后端能力（如本平台的 testgen 引擎、定时任务）没有 UI 入口，强行"转 UI"只能编造操作步骤——这正是"假用例"的来源。

### 发现 4：当前页面提取有重复膨胀，1016 条里约 38 条是重复或假路径

`/Dashboard.vue x6`、`/Index.vue x2`、`/index.vue x2` —— 说明非 router 文件里的 `.vue` 被回退成"用文件名当路径"。这会让用例数虚高，也会让"页面可达"维度对着一个不存在的路由跑。

这是一个独立的缺陷，与"要不要转 UI"无关，但会放大"UI 生成很水"的观感。

## 三、三档方案对比

| 维度 | 方案 A：保持现状 | 方案 B：全部转 UI | 方案 C：分层 + 各自具体化（推荐） |
|---|---|---|---|
| 核心动作 | 不改 | 所有能力改写为 UI 操作步骤 | UI 层补具体化；接口层只覆盖 UI 无法构造的维度 |
| 后端能力（无 UI 入口） | 保持接口用例 | **无法实现**，只能编造步骤 | 保持接口用例，作为该能力的唯一覆盖 |
| UI 用例质量 | 1016 条模板 | 依赖映射，映射不存在则同样模板 | 开启运行时发现后升到"元素级"（真实按钮名、选择器） |
| 可读性 | 一半好（UI）一半差（函数） | UI 部分可读，但步骤可能造假 | 两层都可读，且都可判定 |
| 可操作（人能照着手测） | **差**（异常维度无构造手法） | 名义上强，实际靠编 | **强**（元素名 + 数据 + 构造手法） |
| 改动成本 | 0 | 极高，且需要新的映射数据源 | 中（分 3 步） |
| 风险 | 观感差、用例虚高 | 产出不可信，执行大概率假失败 | 可控，每步可单独验证 |

### 为什么"全部转 UI"不可行（三条硬理由）

1. **无 UI 入口的能力转不了**：定时任务、内部引擎、消息消费者没有页面，转 UI 只能编。
2. **UI 层无法精确构造部分维度**：`top_n=0`、`token 过期`、`越权访问他人资源`、并发竞争——这些在浏览器里手工构造成本极高甚至不可行，接口层一条请求就能稳定复现。
3. **执行成功率会崩**：UI 用例靠 browser-use 跑，元素定位一旦不稳就是 flaky；把 1000+ 条全压到 UI 层，等于把稳定性风险放大一个数量级。

## 四、推荐路线（方案 C，分三步，每步可独立验收）

### 第一步：把 UI 用例从"页面级"升到"元素级"（治"不可操作"）

- 生成时带上 `test_url`。代码里 `if req.runtime_ui or req.test_url or req.login_url: target.enabled = True` —— **只要给地址，运行时发现自动开启**，无需另开开关。
- 开启后 `_runtime_steps` 会把文案换成：`用浏览器打开被测环境地址 http://...（页面标题：XXX）` + `关键元素可见：项目名称、状态、创建时间` + 控制台基线。
- 收益：`定位交互点：DataFactorySelector.vue` → `定位交互点：新建项目、搜索、导出`，从"文件名"变成"用户看到的按钮"。
- 验收标准：随机抽 10 条 UI 用例，无前端经验的人能照着在浏览器里点完。

### 第二步：给 4 个异常维度补"构造手法"（治"7 条同构"）

当前 7 条执行步骤完全相同。应改为每维度独立四步：

| 维度 | 执行步骤应写成 |
|---|---|
| 网络中断 | 打开 DevTools → Network 选 Offline → 刷新页面 → 观察是否有重试/提示 |
| 错误回显 | 提交必填项留空的表单 → 观察是否红字提示且不展示堆栈 |
| 空状态 | 用无数据的账号登录（或过滤到无结果）→ 观察是否显示空状态文案 |
| 错误页 | 用 DevTools 把接口 mock 成 500 → 观察是否展示错误页而非白屏 |

这四段文案是**固定可复用模板**，不需要 LLM、不需要映射数据，纯规则层就能做。

### 第三步（可选）：只对"有 UI 入口的核心流程"做能力-页面映射（治"业务视角"）

- 不做全量映射，只挑 P0 业务流程（如"创建项目→生成用例→查看结果"）。
- 映射来源优先级：PRD/需求文档 > 路由名与接口名的语义匹配 > 人工标注。
- 只有这一类用例走 UI primary，其余接口能力保持接口层，`coverage_role=supplement` 的关联已经现成。
- 需要 LLM 参与（理解业务语义），受免费额度限制，必须限定范围。

## 五、成本与收益（相对当前）

| 指标 | 当前 | 第一步后 | 第二步后 | 第三步后 |
|---|---|---|---|---|
| UI 用例可操作性 | 低 | 中高 | 高 | 高 |
| UI 用例贴题度 | 低（7 条同构） | 中 | 中高 | 高（核心流程） |
| 后端能力覆盖 | 有（接口层） | 有 | 有 | 有（核心流程转 UI 后接口作补充） |
| 用例条数 | 1016（含 38 重复） | 约 978（去重后） | 不变 | 略增 |
| 新增依赖 | — | 被测环境可访问 | 无 | LLM 额度 |
| 需改代码 | — | 否（只传参） | 是（文案模板） | 是（映射 + 范围控制） |

## 六、结论

1. **不要"全部转 UI"**：三分之一以上的能力没有 UI 入口，转了就是编；UI 层也构造不出精确边界和安全用例。
2. **用户的直觉方向是对的**：UI 视角确实更贴近人的理解，但当前 UI 用例只做到了"可读"，没做到"可操作"，所以直接全转只会得到 1000 条更长的模板。
3. **优先做第一步和第二步**：不改架构、不开 LLM、成本低，就能把"可读但不可操作"变成"可读且能照着点"。这两步做完，再决定要不要第三步的映射。
