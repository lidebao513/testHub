## 0. 结论先行（一句话）

文章验证的"AI 探页面生成、Playwright+CI 做稳定回归"分工**与 TestHub 现有路线一致**；当前最该立刻做的是**给 AI 立规范（Skill 层）+ 锁死断言来源纪律**两件低成本高杠杆事，以及修掉**幂等键漏 `selected_paths`** 这一行级正确性缺陷；其余改造（异步化 / 分页 / 拆上帝文件 / 鉴权收窄）应按"低风险先修、部署前必修、重构专项做"的节奏排期，避免一次性大改引入回归。

## 2. 当前代码/功能改进权衡分析

> 依据：`services/testgen/docs/code_review_2026-10-19.md`（A 设计 / B 实现 / C 缺陷 / D 性能 / E 交互，共 25 项，含 2 项本会话已修）与本会话对 `app.py:506-518`（幂等键）的复核。
> 每条按：**现状 → 修改方向 → 好处 → 潜在坏处 → 权衡结论** 展开。

### 2.1 可维护性 / 可读性

**A-1 拆分 `app.py` 上帝文件（1778 行）**
- 现状：所有路由/鉴权/错误处理/静态服务堆在一个文件，改任意端点都碰巨文件，单测需起全 app。
- 修改方向：`APIRouter` 拆分（tasks / scan / projects / repos / llm / quality），`app.py` 仅做 lifespan + 中间件 + `include_router`。
- 好处：单一职责、回归风险↓、端点可独立单测、新端点易加（**可维护性↑、扩展性↑**）。
- 潜在坏处：重构面大；需保证路由前缀/依赖注入一致，过渡期可能引入 import 循环；集成测试 import 路径需同步改（**兼容性风险中**）；短期 PR 体积大。
- 权衡：收益高、成本中高，**适合专项重构，不与功能开发混做**。优先级：中。

**A-4 双层 stage 顺序表过度抽象**
- 现状：`_P1_STAGE_WIRING` 与 `PIPELINE_STAGE_ORDER` 两处硬编码 + `REGISTRY` 间接层，两表不同步即**静默错序**（最危险的"看起来对其实错"）。
- 修改方向：保留单一 `PIPELINE_STAGE_ORDER` 直接映射，移除 `REGISTRY` 间接层。
- 好处：消除静默错序隐患（**正确性↑、可维护性↑**）。
- 潜在坏处：需全量核对现有 stage 顺序不被改坏（**兼容性风险中**），改动涉及 pipeline 核心。
- 权衡：中优先，需配套测试锁定顺序。

**B-4 `quality_summary` 伪并行（注释误导）**
- 现状：`submit(fn).result()` 立即阻塞 = 串行却多一层线程开销，注释却写"并行"。
- 修改方向：`as_completed` 真并发，或如实改注释。
- 好处：性能微升（**性能↑**）、注释诚实（**可维护性↑**）。
- 潜在坏处：极小。
- 权衡：低优先，顺手做。

### 2.2 性能

**A-2 / D-2 同步端点阻塞 worker（/pipeline、/describe、/analyze）**
- 现状：请求线程内同步跑分钟级重计算/LLM，占满线程池，拖垮 `/health`。
- 修改方向：改 `async def` + 丢 `BackgroundExecutor`（与 `/generate` 同机制）；describe/analyze 改"提交→轮询"。
- 好处：吞吐↑、探针不被阻塞、大仓库不卡（**性能↑、健壮性↑**）。
- 潜在坏处：前端轮询逻辑需改造（describe 原同步返回）；错误传播路径需重测（**兼容性风险低-中**）；复用已有 BackgroundExecutor，成本可控。
- 权衡：部署前必做的中优先项，风险可控。

**C-1 / D-1 列表与 cases 接口无分页、轮询大字段**
- 现状：cases 无分页（实测 4359 条 obsolete）；tasks 列表含大 `result` blob，前端每 3s 拉 `limit=20`。
- 修改方向：cases 加分页（`?offset=&limit=`，默认不含 obsolete）；tasks 列表只返轻量字段，`result` 仅详情端点返回。
- 好处：响应体↓、序列化耗时↓、内存峰值↓（**性能↑、可扩展性↑**）。
- 潜在坏处：前端需改分页/摘要逻辑（**兼容性风险中**）；新增参数与交互。
- 权衡：中优先，性能与扩展性关键。

**D-3 TaskStore 每操作开闭 SQLite 连接**
- 现状：每操作 `connect()/close()`，高并发写（进度每阶段一次）多次连接。
- 修改方向：短生命周期连接池，或进度按时间/阶段节流落库。
- 好处：IO 效率↑（**性能↑**）。
- 潜在坏处：连接池需处理线程安全（**复杂度中**）；节流可能丢失细粒度进度（可接受）。
- 权衡：低优先（单机可跑）。

**C-2 / D-4 `replace_*` 写放大**
- 现状：每次生成全表删插功能点/测试点，I/O 放大；failed 后立即重提可能交错覆盖。
- 修改方向：项目级写锁/乐观版本号；增量 upsert。
- 好处：并发安全↑、写放大↓（**健壮性↑、性能↑**）。
- 潜在坏处：锁/版本号增加复杂度；upsert 需保证幂等语义（**复杂度中**）。
- 权衡：中-低优先，仅并发重提场景触发。

### 2.3 健壮性 / 正确性

**A-5 / B-1 幂等键漏 `selected_paths`（最高优先）**
- 现状：`_idem_key_for_generate`（app.py:506-518）不含 `selected_paths` → 同仓库不同子集二次提交返回旧任务（旧子集产物），用户见"生成没生效"。
- 修改方向：键追加 `",".join(sorted(req.selected_paths))`；同步查 `execute`/`dialogue` 其它 idem 路径。
- 好处：修复子集生成正确性（**正确性↑，高优**）。
- 潜在坏处：会改变现有幂等键字符串 → 旧 pending/running 任务的 idem 失效需重提；但 failed/success 本就允许重提，影响可控（**兼容性风险低**）；纯一行改动。
- 权衡：**最高优先、最低成本、最低风险，立即做**（用户已拍板，因本任务延后统一解决）。

**C-1 分页（同 2.2）** — 同时防大项目序列化风险（健壮性）。

**C-3 analyze 截断但 count 全量**
- 现状：返回 `functional_points[:500]` 但 `counts` 全量，前端若用数组长度判断会误判。
- 修改方向：响应显式带 `truncated` 与 `total`。
- 好处：前端判断正确（**正确性↑**）。
- 潜在坏处：前端需读新字段（**兼容性风险低**）。
- 权衡：低优先。

**C-4 cancel 依赖阶段边界检查**
- 现状：协作取消靠每阶段 progress 回调 `is_cancelled`，长时间不回调则延迟生效。
- 修改方向：重计算循环内周期性检查。
- 好处：取消更及时（**健壮性↑**）。
- 潜在坏处：需插入检查点（**复杂度低**）。
- 权衡：低优先。

**E-2 半选组头点击语义歧义**
- 现状：`indeterminate` 组头点击读 `t.checked=true` → 全选，与"取消其余"直觉冲突，可能**误生成过大子集**（与 Playwright E2E 发现一致）。
- 修改方向：`indeterminate` 点击执行明确语义（仅保留已选/全不选）+ UI 文案；或两步 toggle。
- 好处：避免误生成、交互明确（**交互体验↑、正确性↑**）。
- 潜在坏处：需改交互逻辑+前端测试（**兼容性风险低**）。
- 权衡：中优先，影响用户直接操作结果。

### 2.4 安全

**B-2 鉴权形同虚设 + CORS 通配 + 代理 `verify=False`（部署前提）**
- 现状：`require_auth` 未配 token 时全端点免鉴权；`CORS(allow_origins=["*"], allow_credentials=True)`；`proxy.py` `requests` 用 `verify=False`。三者叠加：能访问 8900/8910 的人可 CRUD **仓库 PAT 与 LLM API Key** 并触发生成/执行。本地演示可接受，**部署到局域网/公网即高危**。
- 修改方向：写操作强制 `X-Auth-Token`；CORS 收窄为已知前端源；`verify` 仅 localhost 成立、远程启用校验/证书；CSRF 豁免收敛。
- 好处：安全↑（**部署前提**）。
- 潜在坏处：收紧后本机/演示需配 token，可能打断现有免密调用（**兼容性风险中**）；前端需带 token；远程 verify 需证书管理。
- 权衡：部署前必做，需配套前端/配置改动，排期中优先。

**B-3 proxy 透传全部 header（含 Cookie）**
- 现状：`_do_proxy` 透传除逐跳头外所有头，含 `Cookie`/`Authorization`；iframe 嵌入时主平台登录态转发到 sidecar，存在会话混淆/越权面。
- 修改方向：默认剥离 `Cookie`，仅白名单头（`X-Auth-Token`、`Content-Type`）。
- 好处：减少会话混淆/越权面（**安全↑**）。
- 潜在坏处：若某些流程依赖转发 Cookie 会断（**兼容性风险中**）；需先评估现有依赖。
- 权衡：中优先，需先确认有无 Cookie 依赖。

**A-3 `/ready` 探针有写副作用**
- 现状：`/ready` 调 `init_db()` 建表，只读探针改库；权限收紧场景直接失败。
- 修改方向：`/ready` 只 `SELECT 1`；建表移 `lifespan`（已有）。
- 好处：探针语义正确、收紧权限不崩（**健壮性↑**）。
- 潜在坏处：极小（**风险低**）。
- 权衡：低成本低收益，顺手做。

### 2.5 扩展性

- **A-1 拆分 `app.py`**（见 2.1）同时是扩展性前提：新端点/能力可独立 router 接入，不碰巨文件。
- **前文方案 #1 Skill 规范层**：把"AI 怎么干活"外置为可版本化规范，新场景只需加 Skill 而非改 Agent 代码（**扩展性↑**），代价是规范需维护。

## 3. 统一权衡结论与落地建议

1. **低风险高杠杆，先修**：A-5/B-1（幂等键，1 行）、E-2（组头语义）、A-3（/ready 去写副作用）、B-4（注释）——几乎零回归风险，应随下一次提交一起收掉。
2. **部署前必修**：B-2（鉴权/CORS/verify）、A-2/D-2（异步化）、C-1/D-1（分页）——不修则局域网/公网部署即高危或卡顿。
3. **专项重构做**：A-1（拆 app.py）、A-4（stage 顺序表）——面大，单独排期，配测试防回归。
4. **锦上添花**：C-2/D-3/D-4、B-5、C-3、C-4、E-3~E-6。
5. **与 Playwright 方案合并排期**：前文 9 项（T1）与本文 T2–T8 不应各自为战；在 G1（Django+MySQL 环境）解决后，与本追踪文档第八章 P0–P3 排期合并，统一评审落地顺序与工作量，**避免一次性大改引入回归**。
