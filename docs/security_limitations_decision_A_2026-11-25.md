## 三、为什么选 A：成本收益与残余风险

### 3.1 应用层补 DNS 校验为何被否（S6-c）

在 `check()` 里加 `socket.getaddrinfo` 做"域名解析到内网就拦"看似直接，但会引入 **TOCTOU**：校验时是公网 IP、浏览器真正连接时已变内网。这会产生**虚假安全感**——比明确登记"未根治"更危险。故应用层不做此补强。

### 3.2 B 方案（IP pin / 出口代理）的代价

| 路线 | 需要改动 | 主要代价 |
|---|---|---|
| connection-level IP pin | browser-use / Playwright 网络栈，拦截 DNS 响应并锁定到校验通过的 IP | 触达第三方库网络层，升级即可能失效；与本仓"不改网络栈"红线冲突；需独立回归体系 |
| 强制出口代理 | 统一代理 + 出口策略 | 引入新基础设施与运维面；多租户下代理配置、凭据、审计均为新增课题 |

两者都不是本仓当前阶段能低成本闭环的改造，且**本仓主要用例面向可信目标站点**——残余风险的实际暴露面有限。

### 3.3 保留 A 的依据

- 已知云元数据域名（含混淆写法、十进制整数写法、阿里云 `100.100.100.200`）由**浏览器 DNS 层**钉死，不经 Python 校验、无 TOCTOU，页面脚本无法 rebinding 拿到这些固定域名 IP。
- 302 落点闸门把暴露窗口从"下一步"缩短到"本步结束"，元数据命中恒拦并中止任务。
- 内网段默认 `block`，`UI_ALLOWED_DOMAINS` 可显式放行平台自测地址（:8900 / 局域网 :8099），降级必留痕。
- 三项均有自动化守护测试钉住（见第二节），不存在"文档写拳、代码没做"的空头缓解。

## 四、残余风险（维持现状 = 接受以下风险，不得对外声称已覆盖）

1. **任意内网域名 rebinding**：`internal.corp.com` 解析到 `10.0.0.5` 仍拦不住；浏览器 DNS pin **只覆盖** `_METADATA_HOSTNAMES` 中的固定元数据域名。
2. **302 步内暴露**：跳转在步内已发生，页面内容可能已进入当步快照；落点闸门只缩短窗口，非网络层拦截。
3. **`off` 是运维主动降级**：放开内网段（元数据仍硬拦），平台自测需要；告警可观测但开关保留。
4. **白名单为空的逃生口**：任务里没写 URL 且未配 `UI_ALLOWED_DOMAINS` 时任何模式都不拦（否则 strict 会把功能拦死）；元数据判定不受此逃生口影响。

## 五、B 方案重启触发条件（满足任一即重新评估）

1. 出现**真实攻击证据**：审计日志发现页面脚本 rebinding 到内网域名并成功访问非白名单内网资源；
2. 平台开始承接**不可信外部站点**的自动化任务（当前主要面向可信目标站点）；
3. browser-use / Playwright 升级后提供**官方稳定的网络层拦截点**，改造成本显著下降；
4. 合规 / 安全审计明确要求 connection-level 出口管控（如等保或客户合同条款）。

触发后按新任务重新立项评估，**不自动启动**。
