# 独立「网址生成用例」入口设计（2026-11-23）

> 文档性质：**方案**。本次未修改任何 `.py` / `.js` / `.html` / 测试文件，未运行生成任务。
> 目的：把需求理解、现状盘点、按现有逻辑的落地设计列出来，供对照预期后再决定是否实施。

---

## 0. 结论先行

- **技术上完全可行，且核心链路已经存在**：引擎的「地址通道」（只给被测地址 + 账号密码 → 浏览器发现 → 生成用例）已有端到端验收测试（`services/testgen/tests/test_a2_runtime_cases.py::test_url_only_channel_produces_cases_end_to_end`）。
- **真正要新建的只有两件事**：① 一个专注的入口界面；② 若入口放到主平台，需要把地址/凭证参数从主平台透传到 sidecar（当前主平台这条参数链是断开的）。
- **头号待确认点**：这个「独立入口」到底挂在哪个形态上（sidecar 控制台 / 主平台菜单页 / 独立工具），不同形态的改动量和最终体验差别很大。见第 3.1 节。

## 1. 我对需求的理解（请对照你的预期）

结合前两轮讨论，我理解你要的是：

> 把「输入被测网址 + 账号密码 → 生成测试用例」这件事，从现在那个混杂了代码目录、git、扫描、增量基线、执行验证的**大而全控制台**里独立出来，做成一个**专注、简单、只做这一件事的入口**：填地址/账号 → 点一下 → 出用例。

如果这个理解对，那么它对应的是产品定位里最核心的那条链路（**Web 测试自动化**：输入目标网址+账号密码 → 解析站点 → 出功能点/用例），而不是代码分析那条支线。

**需要你确认的三个理解点：**
1. 「操作」是否**仅指生成测试用例**？（按现有红线，sidecar 只生成不执行；执行验证是另一个独立动作）
2. 输入是否包含**动态码 OTP**？（地址通道支持，但时效只有 30~60 秒）
3. 是否要保留一个单独的「扫描」按钮？（见第 2 节末尾的认知纠正）

## 2. 现状：现有入口盘点与能力缺口

| 入口 | 位置 / 端口 | 支持「地址+账号→用例」？ | 说明 |
|---|---|---|---|
| sidecar 全功能控制台 | `services/testgen/service/web/index.html`，`:8910` | ✅ 支持（已验证） | A 区代码源/git + B 区扫描/全量增量/基线 + C 区智能输入框 + D 区被测地址/账号/密码/OTP + 执行验证全混在一页；`buildBody()` 用 `runtime_ui=!!(test_url\|\|auto_input)` 自动推导地址通道 |
| testhub 主平台集成 | `apps/testgen_integration` + Vue `:3900` | ❌ 当前不支持 | `/api/testgen/generate` → `client.generate()` 只透传 `local_path/repo_url/scopes/changed_files/mode`，**没有 test_url / login_* 参数**；独立控制台页 `console.html`（`/ai-generation/testgen-console`）定位是「分支阶段对比 + 代码生成」，同样不含地址通道 |
| CLI | `services/testgen/cli/main.py` | ✅ 支持（`--url` / `--runtime-ui`） | 命令行入口，无 Web 交互 |

**关键缺口（决定了改动量）：**
- 主平台侧 `client.generate()`（`apps/testgen_integration/client.py:134`）和 `TestgenGenerateView.post()`（`views.py:73`）目前**不透传地址与凭证**。所以如果独立入口做在主平台里，必须先补这条参数链；如果做在 sidecar 控制台里，则几乎零后端改动。

**一个认知纠正（关于「扫描」）：**
- 现有「🔍 扫描」按钮只对**代码源**有意义（列文件树、标变更状态）。
- 地址通道里没有「先扫描代码」这一步——**浏览器发现页面/接口就是事实上的「扫描」，它发生在生成任务内部**，用户不需要也不能单独点。所以独立入口里这一步要么省略、要么重新定义为「预检地址是否可达」。

## 3. 设计：按现有逻辑会做成什么样

### 3.1 入口形态（头号待确认）

| 方案 | 做法 | 改动量 | 优点 | 缺点 |
|---|---|---|---|---|
| **A. sidecar 独立页**（我的推荐，若目标是快速验证） | 在 `:8910` 增加一个专注页面（如 `/url` 或控制台新 tab），只保留地址输入区 + 生成 + 进度 + 结果 | 小 | 完全复用已验证的地址通道与 `runtime_ui` 推导逻辑，后端几乎不动，见效快 | 不是主平台的菜单，没有 testhub 登录/用例回流/任务中心 |
| **B. 主平台独立菜单页**（我的推荐，若目标是产品化） | Vue 新增页面（如 `/ai-generation/url-to-cases`）+ Django 新端点 + client 参数透传 | 中 | 真正融入平台：登录鉴权、可回流 TestCase、任务中心、报告；契合「Web 测试自动化平台」定位 | 需改前端页面/路由 + Django 视图 + client + 测试 |
| **C. 完全独立工具** | 独立 HTML 单页或 CLI 子命令 | 小~中 | 极致独立 | 与平台割裂、重复建设凭证/轮询/鉴权 |

> 我倾向 **B**（如果你把它当产品功能），或 **A**（如果你只是想先有个干净入口验证）。请你拍板。

### 3.2 页面字段（输入区，按现有能力裁剪）

- **被测地址 URL**（必填）——对应 `test_url`；入口若是 `/login` 会自动拆出站点根地址
- **登录页地址**（可选）——对应 `login_url`，不填则用 URL
- **账号 / 密码**（可选）——对应 `login_user/login_password`；不填走匿名访问（仍会打开地址）
- **动态码 OTP**（可选）——对应 `login_otp`，建议临近生成时填
- **项目名**（可选）——缺省自动命名
- **行为维度**（可选）——正常/异常/安全/边界，缺省为默认集
- **显式路由**（可选）——高级项，对应专家反推/手动 routes

### 3.3 操作流（输入 → 结果，端到端）

1. 填输入 → 提交前**预检**：地址格式、OTP 时效提醒、是否已有任务在跑（避免幂等键撞车）
2. 提交：`POST` 生成端点 → 返回 `task_id` + `poll_url`（202）
3. 轮询进度：阶段名沿用现有（`浏览器发现页面/接口 → 功能点提取 → 测试点展开 → 用例生成 → 质量门禁`）
4. 完成：展示 KPI（三通道 body/impact/runtime）+ 用例列表（可按通道过滤）+ **0 条诊断**
5. 可选：把用例**回流**到 testhub 用例库（走现有 `/api/testgen/sync`，`tg:<tc_no>` 幂等）

### 3.4 后端链路：复用 vs 新增

- **完全复用**：引擎 18 阶段、`/api/v1/generate` 异步任务、幂等键、凭证掩码（`_redacted_request` 把账号/密码/OTP 打码）、报告、0 条诊断逻辑
- **按形态新增**：
  - 形态 A：一个 HTML 页 + 精简版 `buildBody()`（固定 `runtime_ui=true`、`local_path=""`）
  - 形态 B：`client.generate()` 增 `test_url/login_*` 参数 + `TestgenGenerateView` 透传 + Vue 页面/路由 + （可选）专用端点 `/api/testgen/generate-by-url`

### 3.5 关键边界与既有约束（必须沿用）

- **生成-only 红线**：`execute/exec_url` 一律被拒；执行验证另走独立入口
- **鉴权**：sidecar 用 `X-Auth-Token`（当前 `.env` 已恢复 token）；主平台用 `IsAuthenticated`
- **环境开关**：`RUNTIME_UI_ENABLED` 必须保持 `off`（当前就是 off）；改成 on 且不给地址会直接快速失败
- **登录失败分类提示**：区分「被测系统 SSO 网关不可达」与「账号/动态码错误」
- **凭证不落库、不入产物**：只经请求/`.env` 注入
- **幂等键含地址指纹**（`_runtime_sig`）：换地址不会误命中旧任务的产物
