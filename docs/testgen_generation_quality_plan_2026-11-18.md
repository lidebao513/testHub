- 基线结果：变更 7 文件 / 20 hunk → 91 功能点 → 保留 2 → 测试点 2 → 用例 2（全部 reused）

## 0. 结论摘要

| 问题 | 结论 | 推荐方案 | 预估效果（同一份 diff，scope=正常+异常+边界） |
|---|---|---|---|
| ① 只测改动本体，不测历史影响 | 属实，收窄只做「函数体 ∩ hunk」，无调用图扩散，无「受影响」标签 | **分层影响面（L0 直接改动 / L1 一跳调用方 / L2 共享契约 / L3 同模块冷区）**，按入口聚合后出「回归」用例 | 2 → 2 本体 + 3~5 条回归 |
| ② 覆盖度太粗 | 维度是「类型级模板」，与变更语义无关；无路由页面被压成 1 档；scope 只勾「正常」 | **变更语义标签 × 维度路由表**，叠加类型模板，新增 7 个语义维度 | 每变更页 1 → 4~7 维度 |
| ③ 数量不够 | 大头在运行时通道（历史 45 条）与 scope 类别，不在代码规则 | **三通道互补 + 维度矩阵 + 影响面**，并定义三个覆盖率 KPI | 总计 14~19 条（代码通道） |
| ④ 能否去掉测试点层 | 当前 TP→Case 严格 1:1（`tc_no = tp_id`、title 相同），TP 是**冗余存层** | **不删，改契约**：TP = 可断言命题，Case = 执行方案；仅当多策略时 1 TP→N Case | 数量不变，省一次落库与约 40% 冗余字段 |

一句话：**先让「改动」不再被吞掉（①），再让「每条用例有具体命题」（②），最后用影响面与三通道把覆盖面补全（③）；TP 层不是数量瓶颈，是契约设计问题（④）。**

## 2. 问题①：改动 + 历史功能影响

### 2.1 目标（DoD）

1. 每条因变更产出的用例，必须能标注来源：`direct`（改动函数本体）或 `impact`（受改动影响的历史入口）；
2. 后端改动落在私有/被吞并函数时，**不允许消失**，必须归属到调用方入口；
3. 影响面条目必须写明「因为 X 改动，验证 Y 未回归」，而不是泛化模板；
4. 影响面条目数有预算上限，不因 20 个调用点炸成 20 条。

### 2.2 方案对比

| 方案 | 做法 | 覆盖 | 成本 | 误报风险 | 结论 |
|---|---|---|---|---|---|
| A 文件级影响 | 改动文件内所有 FP 都标「受影响」 | 高 | 极低 | 极高（一个 8000 行文件全中） | 否，等于回到 208 条 |
| B 同文件调用图（1~2 跳） | 复用 `_callers_index` 反向扩散，路由为边界 | 中高 | 低（已有能力，仅同文件） | 低 | **推荐为 L1** |
| C 跨文件全局图 | 解析 import/export 建全仓图 | 最高 | 高（Python+TS 双语言） | 中 | 二期，仅前端组件 props |
| D 语义+图混合 | 图定候选，语义定是否真受影响（改的是签名/返回值/共享状态） | 高 | 中 | 低 | **推荐组合** |

关键事实：本次 `_record_thread_activity` 的 **20 个调用点全在 server.py 同一文件内**，所以方案 B 零新增基础设施即可命中；前端 `onSessionCreated` 跨 `PcChatPage`→`PcShell` 两个文件，需轻量跨文件索引（按导出名匹配），列为二期。

### 2.3 推荐：分层影响面（L0~L3）

| 层 | 定义 | 产出标签 | 用例维度 | 置信度 | 预算 |
|---|---|---|---|---|---|
| L0 直接改动 | FP 的代码范围 ∩ hunk | `更新` | 该 ftype 完整维度 | 1.0 | 不限（受维度矩阵约束） |
| L1 一跳调用方 | 反向调用图中，直接调用改动函数的路由/业务函数 | `受影响·直接` | 回归-主流程未变（REGRESSION_FLOW） | 0.8 | ≤3 条/改动函数 |
| L2 共享契约 | 改动函数写入/返回的数据结构被其他入口读取（同文件内按返回值字段名匹配） | `受影响·数据` | 回归-数据形状兼容（CONTRACT_SHAPE） | 0.6 | ≤2 条/字段 |
| L3 同模块冷区 | 同模块内未被调用但与改动函数共享全局状态/常量 | 不进用例，只进报告 | — | 0.3 | 0（仅提示） |

L1 的聚合规则（防膨胀）：

```
受影响入口 = 调用点所在的最外层"入口函数"（路由处理器或 @app 生命周期钩子）
若同一入口有 N 个调用点 → 合并为 1 条用例，断言列 N 个场景
若受影响入口 > 预算 → 按调用点数量降序取前 N，其余写入「未覆盖影响面」清单
```

映射到本次：

| 受影响入口 | 调用点行号 | 产出 |
|---|---|---|
| `chat()`（POST /api/v1/chat） | 4533/4567/4613… | 1 条：首轮消息标题写入与复用 |
| 会话创建路由 | 4649/4683/4694 | 1 条：预留会话 → 首次发消息后标题回填 |
| 会话收尾（streaming=False） | 4707/4736 | 1 条：空消息不覆盖已有标题 |
| `/api/v1/threads` 详情/列表 | 4921/4954 | 1 条：列表返回 title 与前端一致 |

### 2.4 数据结构

```python
# engine/impact.py（新建）
@dataclass(frozen=True)
class ImpactEdge:
    changed_func: str        # 被改函数（qname）
    entry: str               # 受影响入口（路由/钩子）
    hops: int                # 1 或 2
    call_sites: tuple[int, ...]  # 调用点行号（证据）
    kind: str                # "call" | "data"

@dataclass
class ImpactSet:
    direct_fp_ids: set[str]
    affected: list[ImpactEdge]
    truncated: list[ImpactEdge]   # 超出预算的部分，进报告不进用例
    stats: dict[str, int]         # changed_funcs / entries / dropped
```

打标扩展（`diff_tag.py`）：

- `更新`：改动本体（现有）
- `受影响·直接`：L1
- `受影响·数据`：L2
- 前端页面若同时是 L0 与 L1 来源，标签优先级 `更新 > 受影响`

### 2.5 收敛与误报控制

1. **只对「改动函数真实被调用」的路径扩散**，不做同模块全量；
2. **入口必须是路由/生命周期**，纯工具函数之间的调用不算入口；
3. 影响面用例的 `expect` 必须写成「原有行为 X 保持不变」，不能写「功能可用」；
4. 每条影响面用例必须带 evidence（调用点行号），无证据不出点；
5. 影响面条目上限：每个改动函数 ≤3 条，整次生成 ≤ 变更函数数 × 3。

### 2.6 与「变更靶向」的关系

`change_targeting.py` 已能从变更推出「该测哪些地址」，但它服务运行时匹配，不产用例。改造后两者共用同一份 hunk 与调用图：

```
hunk → 改动函数 → {直接维度, 影响面入口} → 测试点 → 用例
                              ↘ change_targeting（地址匹配）
```

## 3. 问题②：覆盖度太粗

### 3.1 根因拆解

| 层级 | 表现 | 属于 |
|---|---|---|
| 维度选择 | 只按 ftype 给固定维度，不看 hunk 内容 | 规则缺口 |
| 维度集合 | 无路由页面只有 1 档；缺「流程/分页/契约」维度族 | 能力缺口 |
| 过滤 | scope 只勾「正常」 → 安全/异常/边界全过滤 | 配置 |
| 断言文案 | 「交互元素可用，不新增控制台错误」不可判定 | 模板缺口 |

### 3.2 方案：变更语义标签 × 维度路由表

新增 `engine/change_semantics.py`：从 hunk 文本 + 文件类型推导语义标签（规则 + 关键词权重，不做 LLM）。

| 语义标签 | 识别信号（hunk 内） | 适用 ftype | 追加维度 |
|---|---|---|---|
| `list_mutation` | `setState`/`splice`/`push`/`\[\.\.\.`/`useState`/`map(` | PAGE/UI/COMPONENT | 新增项立即可见、顺序与滚动位置 |
| `dedupe` | `some(`/`includes(`/`has(`/`Set(`/`Map(` | PAGE/UI | 重复项不重复插入 |
| `pagination` | `offset`/`limit`/`cursor`/`page`/`has_more`/`fetchedCount` | PAGE/UI/API | 续页不重不漏、偏移与服务端一致 |
| `branch_mode` | `mode`/`channel`/`office`/`daily_perf`/`if.*===` | PAGE/UI/API | 渠道隔离、切换后状态一致 |
| `fallback` | `\|\|`/`??`/`or "`/`默认`/`未命名`/`fallback` | 全部 | 空值回落、旧数据兼容 |
| `contract_shape` | 返回类型变化（`+ 字段` diff）/`interface`/`Promise<{` | API/前端 api | 返回结构兼容（新增字段不破坏旧消费方） |
| `guard_negative` | `is not None`/`!== null`/`!== undefined`/truthy 改法 | BUSINESS/API | 空值与零值区分（回归重点） |
| `auth_touch` | `Depends`/`middleware`/`token`/`permission` | API | 未授权、越权（现有维度，仅加权） |

维度路由表（新常量）：

```python
SEMANTIC_DIMS: dict[str, tuple[tuple[str, str], ...]] = {
    "list_mutation": (
        (TPType.NORMAL.value, "LIST_INSERT_VISIBLE"),
        (TPType.BOUNDARY.value, "LIST_ORDER_CONSISTENCY"),
    ),
    "dedupe": ((TPType.ABNORMAL.value, "LIST_DEDUPE"),),
    "pagination": (
        (TPType.BOUNDARY.value, "PAGINATION_NO_OVERLAP"),
        (TPType.BOUNDARY.value, "PAGINATION_OFFSET_SYNC"),
    ),
    "branch_mode": ((TPType.NORMAL.value, "BRANCH_ISOLATION"),),
    "fallback": ((TPType.BOUNDARY.value, "FALLBACK_DEFAULT"),),
    "contract_shape": ((TPType.BOUNDARY.value, "CONTRACT_SHAPE"),),
    "guard_negative": ((TPType.ABNORMAL.value, "GUARD_ZERO_VS_EMPTY"),),
}
```

合并规则：

```
final_dims = (type_plan ∩ scope) ∪ (semantic_dims ∩ scope)
if 增量收窄: 不再整体收敛成 1 档，改为「语义维度保留 + 类型维度只留 1 个核心」
```

这直接替换现有 `_NARROW_PLAN` 的粗暴交集——**收敛的目标从「砍维度」改为「换成更贴题的维度」**，条数仍然可控（语义标签通常 1~3 个），但命题变准。

### 3.3 需要新增的维度（枚举扩展）

| 维度 | 归类 | 断言（可判定） |
|---|---|---|
| `LIST_INSERT_VISIBLE` | 正常-新增项立即可见 | 新建后 1 秒内列表出现该 id，且位于预期位置 |
| `LIST_DEDUPE` | 异常-重复项不重复插入 | 同一 id 触发两次插入，列表长度只 +1 |
| `LIST_ORDER_CONSISTENCY` | 边界-顺序与滚动位置 | 插入后顺序符合时间倒序，滚动位置不跳变 |
| `PAGINATION_NO_OVERLAP` | 边界-续页不重不漏 | 连续取 3 页，id 集合无交集，总数等于 has_more 收敛值 |
| `PAGINATION_OFFSET_SYNC` | 边界-偏移与服务端一致 | 本地插入 N 条后，下一次请求 offset = 服务端去重后长度 |
| `BRANCH_ISOLATION` | 正常-渠道隔离 | office 新建不出现在 daily_perf |
| `FALLBACK_DEFAULT` | 边界-空值回落 | 空标题/缺字段时展示默认文案，不显示空 |
| `CONTRACT_SHAPE` | 边界-返回结构兼容 | 新增字段存在且旧字段不变，旧消费方不报错 |
| `GUARD_ZERO_VS_EMPTY` | 异常-空值与零值区分 | `""` 与 `None` 走不同分支，行为符合预期 |
| `REGRESSION_FLOW` | 回归-主流程未变 | 改动前可用的主流程仍成功 |
| `REGRESSION_DATA` | 回归-数据形状兼容 | 读取方拿到旧字段仍可用 |

新增 11 个维度，均属「行为维度-子维度」命名规范，与现有枚举一致。

### 3.4 无路由页面的处理

现状：`has_route=False` → 只有 INTERACTIVE。改进两条：

1. **文件级路由反查**：用 `change_targeting` 已有的「页面文件名 → 路由路径」映射（`PcChatPage` → `/chat` 或 `/pc/chat`），命中则升级为有路由页面，可用完整 7 维度；
2. **运行时补路由**：运行时发现拿到 `reachable_pages` 后，按文件名/标题回填 `has_route=True`（现在 `_runtime_fp_in_target` 已有页面匹配逻辑，可直接复用）。

未命中时保留 INTERACTIVE，但**叠加语义维度**（不再只有 1 条）。

### 3.5 断言可判定化

当前 `expect` 是固定模板。改造：维度 → 断言模板带占位符，由 FP/运行时信息填充：

```
模板：新建{对象}后，{位置}出现该{对象}，且{数量约束}
填充：新建会话后，左侧历史列表首屏出现该会话，且不重复
```

规则校验（生成后自检）：`expect` 必须含「可观测对象 + 期望状态」；不含则判 `unverified=True`，前端标黄。

### 3.6 scope 默认值建议

面板默认勾选现状待确认（本次 `scope_summary={"正常":2}`）。建议默认：`正常 + 异常 + 边界`，`安全` 默认勾选但 `性能` 默认不勾（执行成本高）。这一项零代码成本，收益最大。

## 4. 问题③：全面、准确、不偏移

### 4.1 「偏移」的三种表现

| 表现 | 例子 | 根因 |
|---|---|---|
| 漏（假阴性） | 后端改了却没一条用例 | R1/R2/R3 |
| 泛（假阳性） | 改分页却出「参数非法」 | R5 |
| 错层 | 前端页面变更出「接口鉴权」 | ftype 与语义不匹配 |

### 4.2 准确性：hunk → 断言 → 可执行

三级对齐，每级都有校验：

| 级 | 输入 | 输出 | 校验 |
|---|---|---|---|
| 1 变更定位 | hunk | 改动函数 + 行号 | 函数范围必须覆盖 hunk，否则回落 L0 文件级并标 `unverified` |
| 2 语义推导 | hunk 文本 | 语义标签（1~3 个） | 标签必须能映射到 ≥1 维度，否则该标签丢弃 |
| 3 断言生成 | 维度 + FP/运行时 | 可判定 expect | 必须含可观测对象与数量约束 |

### 4.3 全面性：三通道互补

| 通道 | 覆盖什么 | 现状 | 目标 |
|---|---|---|---|
| 代码通道（改动） | 改了什么 | 2 条 | 本体 + 语义维度，8~12 条 |
| 影响面通道（新增） | 改动影响什么 | 0 | 3~5 条 |
| 运行时通道 | 真实界面元素与可达性 | 0（SSO 503） | 恢复后 40+ 条 |

三者用同一份 `run_batch_id` 聚合，前端按「本体 / 影响 / 运行时」三栏展示，避免混在一起看不清来源。

### 4.4 抑制膨胀

| 手段 | 规则 |
|---|---|
| 靶向 | 只对勾选文件 + 变更文件生成（现有 `selected_paths`） |
| 维度预算 | 每个 FP ≤4 个维度（语义维度优先于类型维度） |
| 影响面预算 | 每改动函数 ≤3 条，按调用点数量降序 |
| 去重 | 同 FP 同维度只留 1 条（现在靠 tp_id 天然唯一，改造后需显式去重键 `fp_id::dimension`） |
| 量级守护 | 复用 `magnitude_guard`，超过上次同类运行的 2 倍则告警并提示原因 |

### 4.5 三个覆盖率 KPI（进报告与前端）

```
变更函数覆盖率 = 至少被 1 条用例覆盖的改动函数 / 全部改动函数
影响面覆盖率   = 被覆盖的受影响入口 / 识别出的受影响入口
维度覆盖率     = 实际维度数 / 该变更适用维度矩阵的理论值
```

本次基线：1/1（但实际改动被跳过，真实应为 0/1）、0/5、2/—。目标：1/1、≥4/5、≥70%。

### 4.6 质量门禁（生成后自检）

一条用例进入产物前必须满足：

1. 有 evidence（文件:行 或 运行时页面/元素）；
2. `expect` 可判定（含对象 + 期望状态）；
3. 有 `coverage_role`（primary / supplement）；
4. 来源标签明确（更新 / 受影响·直接 / 受影响·数据）；
5. 若是影响面条目，正文必须含「因 X 改动，验证 Y 未回归」。

不满足的进入 `unverified` 列表，前端可见但不计入覆盖度。

## 5. 问题④：能否去掉测试点层

### 5.1 事实核查

| 观察 | 证据 |
|---|---|
| TP → Case 严格 1:1 | `case_gen.py:365-397`，注释「1:1 对应（契约不变）」 |
| 用例号就是 TP 号 | `tc_no = TP-xxxx`，`test_cases.json` 中 `tc_no == tp_id` |
| 标题完全相同 | 用例 title 与测试点 title 逐字一致 |
| 步骤是模板 | `doc_steps` 由 `build_doc_steps` 按 kind 套模板，不含 TP 的语义 |
| 幂等键依赖 TP | `tc_no = tp_id`，复用时按 TP 号匹配 |
| 唯一真实差异 | 用例多了执行层信息（ctype / priority / 步骤 / 断言 / 覆盖角色） |

结论：**当前 TP 层是「存了两次的同一件事」**，它没有承担任何"展开"职责。数量瓶颈在 `FP × 维度`，不在 TP。

### 5.2 三个选项

| 选项 | 做法 | 收益 | 代价 | 建议 |
|---|---|---|---|---|
| A 直接删除 TP 层 | pipeline 跳过 `stage_test_points`，`case_gen` 直接吃 `(fp, dimension)` | 少一次落库、少一份产物、字段冗余降约 40% | 失去「可评审的命题层」；traceability 需重写；幂等键换 `fp_id::dimension`；前端测试点页/覆盖度报表要改 | 不推荐 |
| B TP 降级为内存中间量 | 合并成「用例草案」一个产物，UI 只展示用例 | 同上，且前端改动更小 | 同上，且历史数据迁移 | 可选 |
| C TP 保留、改契约 | TP 定义为「一条可断言命题」（含 dimension/expect/evidence），Case 定义为「该命题的一种执行方案」；仅当多策略（UI 层 + API 层）时 1 TP → N Case | 保留评审与覆盖度能力；多策略时才有真正价值；与②的维度扩充天然契合 | 需要 case_gen 支持多策略展开（现在只有一个 strategy） | **推荐** |

### 5.3 为什么推荐 C

1. ② 的维度矩阵会让 TP 从「1 FP = 1 TP」变成「1 FP = N TP」，TP 立刻有了存在价值；
2. 将来同一命题在 UI 层与 API 层各执行一次（`ui_first` / `api_first`），1 TP → 2 Case 才有意义；
3. 保留 TP 则覆盖度 KPI、评审状态、`orphan_tp` 校验全部不用重写；
4. 你现在的痛点是"只有 2 条且很粗"，删层不会让它变多或变准。

### 5.4 若坚持删除，需要同步改的清单（供评估）

| 项 | 位置 | 改动 |
|---|---|---|
| 阶段编排 | `pipeline.py` | 去掉 `stage_test_points`，改由 `stage_cases` 内部展开 |
| 幂等键 | `service/app.py` / `cases` 表 | `tc_no` 从 `tp_id` 改为 `fp_id::dimension` 哈希 |
| 追溯 | `traceability` 统计 | `fp → case` 两栏，去掉 `orphan_tp` |
| 前端 | `index.html` | 测试点页签、覆盖度报表、`orphan_tp` 提示 |
| 历史数据 | `data/testgen.db` | 311 条 obsolete 用例的关系重建 |
| 测试 | `tests/test_*` | 所有断言 `tp_count` 的用例 |

成本约 2~3 人日，收益仅是存储与一次落库。**不建议在这个阶段做。**
