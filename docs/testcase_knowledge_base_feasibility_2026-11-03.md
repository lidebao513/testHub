# 可行性分析：用「历史用例/测试点」构建知识库反哺用例生成

> 想法原文：把生成的测试用例或分析点放入知识库，后续生成其他测试用例时，以知识库里的用例作为基础数据做分析，提升生成用例和测试点的方法。
> 状态：**仅分析，未实施**。日期：2026-11-03。

---

## 一、结论先行

**可实现，而且地基比预期好。但有三个判断必须先纠正：**

| 判断 | 说明 |
|---|---|
| ✅ **可做，且不需要从零搭** | 项目已有 `KnowledgeBase` 框架（含前端界面）、`PromptConfig` 提示词管理、`GeneratedTestCase` 完整生命周期状态、`advanced_analyzer` 测试点分析器——四个关键零件都在 |
| ❌ **不能直接复用现有 KB 表结构** | 现有 KB 是**财务四元组**（公司/报告期/指标/数值），为 LLM 评审的 ground truth 服务；用例是「标题/前置/步骤/预期/优先级」，结构完全不匹配，必须新建领域模型 |
| ⚠️ **真正的提升不来自"存起来"，来自"提炼方法"** | 只做「存用例 + 生成时塞几条例题」是 few-shot，提升有限且会加剧同质化；**真正提升"方法"的是从历史用例归纳出测试点规则库**（第三期） |

**推荐起步方式**：不要一上来建知识库。先用「已批准用例直接作为 few-shot」验证价值（约 1 天工作量），确认有效再建库。理由见 §8。

## 三、把想法拆成 4 个能力（模糊需求 → 可判定项）

| 能力 | 你的原话对应 | 可行性 | 难度 |
|---|---|---|---|
| **A 采集**：用例/分析点入知识库 | 「放入知识库」 | ✅ 可行 | 低（有 status 门 + 快照化） |
| **B 质检**：只有高质量样本才入库 | 隐含 | ✅ 有条件（二值门可用，加权需补 score） | 中 |
| **C 召回**：生成时取相关历史样本 | 「根据知识库用例做基础数据」 | ✅ 可行（两条路线，见 §4） | 中 |
| **D 提炼**：从样本归纳「测试点方法」 | 「提升生成用例和测试点的方法」 | ✅ 可行，**这是真正的价值所在** | 中高 |

> 关键洞察：**A+B+C 是 few-shot，D 才是"方法提升"**。只做前三项，生成结果会越来越像历史用例（同质化），遇到新业务类型仍然弱；做了 D，才能把「金额字段怎么测」这类经验沉淀成跨项目可用的规则。

## 四、三条技术路线对比

| 路线 | 做法 | 依赖 | 成本 | 效果 | 建议 |
|---|---|---|---|---|---|
| **路线 1：结构化 + 标签/关键词召回** | 用例入库时打标（模块/业务域/用例类型：边界值/等价类/异常流/权限/并发/数据一致性…），生成时按需求文本关键词 + 同模块匹配，取 Top-K | **零新依赖**（Django ORM + MySQL 全文/`icontains`） | 低 | 中（召回率靠标签质量） | ✅ **一期就用这个** |
| **路线 2：向量语义召回** | 用例文本 → embedding → 本地索引/向量列，按相似度取 Top-K | 需 embedding 服务（现有 provider 里 SiliconFlow/Qwen 有 bge 系；DeepSeek 无 embedding）+ 索引存储 | 中（含按次调用成本） | 高（跨表述匹配强） | 🟡 二期，先用路线 1 验证价值 |
| **路线 3：方法蒸馏（规则库）** | 定期批量分析高质量用例，归纳出「测试点模式」：如"金额字段 → 0/负数/精度/千分位/币种/上限溢出"；产出结构化规则表，生成时作为**方法论上下文**注入 | 复用现有 LLM 调用 + `llm_budget` | 中（一次性批量） | **最高**（可跨项目迁移） | ✅ **一期末/二期并行**，这是"提升方法"的正解 |

**推荐组合**：路线 1 先跑通闭环拿指标 → 路线 3 提炼方法库 → 路线 2 在样本量够（≥500 条）后再上。

## 五、数据模型草案（建议，不写代码）

```
CaseKnowledge          # 用例知识（一条 = 一个可复用样本）
  ├ project / module / business_domain      # 隔离与召回维度
  ├ case_type        # 功能/边界/异常/权限/并发/数据/兼容/性能
  ├ tags[]           # 人工+规则标签
  ├ title / precondition / steps / expected  # 文本快照（不是外键！）
  ├ source_case_id / source_app              # 溯源：requirement_analysis | testcases | testgen
  ├ quality_signal   # approved/adopted + 评审通过率 + 采纳后是否发现缺陷
  ├ embedding        # 可选，二期
  └ is_active

AnalysisPointKB        # 测试点方法库（D 的产物）
  ├ test_type        # 功能/UI/性能/安全/数据/兼容
  ├ point_pattern    # "金额字段边界" 这类模式名
  ├ trigger_condition# 什么需求特征触发本条
  ├ checklist[]      # 具体检查项清单
  ├ evidence_case_ids[]  # 由哪些用例归纳而来（可追溯）
  └ confidence / usage_count / hit_rate   # 用了多少次、有效多少次

KBUsageLog             # 生成→采纳的回流（证明提升的唯一依据）
  ├ generation_task_id / kb_item_ids[] / prompt_tokens
  ├ adopted_count / rejected_count
  └ review_pass_rate
```

两个设计要点：
1. **快照而非外键**：源用例被删改后，知识库内容不能失效（现有 `kb_service` 也是导出 JSON 的快照思路）。
2. **必须留溯源字段**：否则无法回答「这条规则是哪几条用例归纳的」，评审时无法追责。

## 七、风险与坑（含本项目特有）

| # | 风险 | 具体表现 | 缓解 |
|---|---|---|---|
| 1 | **垃圾进垃圾出** | 未评审用例入库 → 生成质量下降 | 只收 `approved/adopted` + 评审通过；`rejected` 单独存"反例库"（也是资产） |
| 2 | **上下文预算爆炸** | 用例步骤长，塞 5 条就上万 token；browser-use 本身已很贵 | Top-K 上限 + 每条截断 + 总长度预算；复用 `llm_budget` 日预算护栏 |
| 3 | **同质化** | 越用越像历史用例，新业务覆盖不到 | 显式要求"不要重复样例已覆盖的场景"；保留一定比例的"无 KB"生成 |
| 4 | **跨项目泄露** | A 项目用例被 B 项目召回 | `project` 维度硬隔离 + 显式"共享库"开关 |
| 5 | **两类用例混杂** | 业务用例（requirement_analysis）与代码级用例（testgen）语义不同，混一起污染召回 | 分命名空间：`source_app` 区分，召回时不跨类 |
| 6 | **无评分字段** | 无法按质量加权 | 一期用二值门（approved/adopted）；二期补 `TestCaseReview.score` |
| 7 | **效果无法证明** | 说不清是 KB 带来的还是模型变了 | 必须做 A/B：同批需求，开/关 KB 各生成一次，比评审通过率、人工修改率、缺陷发现数 |
| 8 | **中文关键词召回率低** | 同义表述（"登录失败" vs "认证异常"）匹配不上 | 一期靠**人工标签 + 规则**（用例类型枚举）而非纯关键词；路线 2 解决语义问题 |

## 八、为什么建议「先不建库」（最小验证优先）

你真正想确认的是：**"参考历史用例能不能让新生成的用例更好"**。这个假设可以用 1 天验证，不需要先建库：

1. 从 `GeneratedTestCase` 取 20 条 `status in (approved, adopted)` 的高质量用例；
2. 手工拼进 `PromptConfig(writer)` 末尾作为 few-shot；
3. 用同一份需求，开关各生成一次，人工对比。

- **如果对比明显提升** → 值得投入建库（A→B→C→D 全链路）；
- **如果提升不明显** → 问题不在"没有知识库"，而在提示词/模型/需求解析，建库只会白花成本。

这是本项目一贯的「先验证再建设」原则。

## 九、分期建议与验收

| 期 | 内容 | 验收指标 | 预估 |
|---|---|---|---|
| **0 期（验证）** | 手工 few-shot 注入，A/B 对比 | 评审通过率提升 ≥10pp 或人工修改率下降 ≥20% | 1 天 |
| **一期** | `CaseKnowledge` 模型 + 质量门入库 + 路线 1 结构化召回 + `{kb_examples}` 占位符 | 生成时日志可见「召回 N 条同类用例」；A/B 指标可复现 | 3-5 天 |
| **二期** | `AnalysisPointKB` 方法蒸馏（路线 3）+ `KBUsageLog` 回流 | 规则库 ≥30 条；命中率/有效率可统计 | 5-8 天 |
| **三期** | embedding 语义召回（路线 2） | 召回率对比路线 1 提升；成本可控 | 视样本量 |

## 十、与当前 14 项优先级的关系

**不冲突，但建议插在 P1 之后**，原因：

1. **强依赖 #181（三层断言）**：KB 的质量门需要"用例好坏"的可测信号；三层断言做完后，"生成→执行→是否真通过"才成为可靠的质量标签。
2. **不依赖 #177/#178/#179**：预探索、模型分级、内网拦截是 UI 执行侧的事，与用例生成为两条链路，可并行。
3. **天然位置**：`#183 生成-执行-回流闭环` 完成后，KB 正好接在"回流"之后做二次利用——**回流产生数据，KB 消费数据**。

建议排期：**P1 结束（#180/#181/#182 合并后）→ 插入本方案 0 期验证 → 一期建设**，与 P2 的 #121 并行。
