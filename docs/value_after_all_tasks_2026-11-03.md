## 一、基线：现在的 TestHub 是什么

### 1.1 已建成的骨架（这部分不会因 14 项而改变，是地基）

| 层 | 现状 |
|---|---|
| 生成侧 | 需求分析生成用例（多 Provider）+ testgen 代码扫描生成用例（含远程只读扫描、分支/提交、子集生成、阶段对比 C1-C3） |
| 执行侧 | UI 自动化（browser-use 深度定制，`ai_base.py` **2289 行**）、API 测试、性能测试、app 自动化 |
| 治理侧 | 八环门禁（secret/lint/format/enum/structure/type/security/test，覆盖率 82%）+ 远程 CI 绿 + **main 分支保护已生效**（gate/pr-lint 必需、enforce_admins） |
| 安全侧 | G3 安全裁决、G4 执行后裁判钩子、JWT httpOnly Cookie、monitor SQL 防护、prompt 注入守卫、成本护栏 `llm_budget`（四道闸） |
| 资产侧 | 缺陷、报告、评审、版本、任务中心、执行记录（`AIExecutionRecord`） |

### 1.2 三个真实天花板（14 项正是为此而排）

**天花板一：能跑，但不完全可信。**
`AIExecutionRecord` 只有 `status`（passed/failed），没有「为什么算通过」的自动证据链；断言靠 `assert_type/assert_value` **人工填**。Agent 说「我做完了」就落 `passed`。

**天花板二：能跑，但不敢放大。**
- `ActionGuard` 默认 `domain_mode='warn'` —— **只记日志不拦截**；
- 无内网/云元数据段识别（`169.254.169.254` 可访问）；
- 无 session 级隔离（只有 tab 级 `agent_focus_target_id`）；
- 并发多任务存在串台风险。

**天花板三：成本不可预测、也不可证明。**
`AIExecutionRecord` **无 token/cost 字段**；成本只落在 `llm_budget` 的文件（`usage_path`）里。browser-use 每步重塞完整 DOM，一条 20 步用例几十万 input token；现在既无法按用例归因，也无法证明「分级路由省了多少」。

补充一个薄弱点：`apps/ui_automation/` 真正有内容的测试文件只有 **2 个**（`test_cost_guard.py`、`test_prompt_injection_guard.py`），相对 2289 行核心文件严重偏薄。

## 二、14 项全部完成后，三类形态改变

### 改变一：从「用例生成器」变成「执行闭环」

| 现在 | 完成后 |
|---|---|
| 需求/代码 → 用例（生成完就断） | 需求/代码 → 用例 → AI 执行 → 三层断言 → 报告回流 |
| 执行靠人工点，结果靠人看 | 定时冒烟巡检自动跑，产出报告+截图+结论 |
| 分支改动影响哪些用例：不知道 | C4 阶段对比：可查两阶段用例差异 |
| 需求/生成/执行/报告四套体系各自为政 | 编排层串成一条链路（新-8） |

**形态差异**：平台从「帮你写用例的工具」变成「帮你跑完并给出结论的系统」。这是**产品定位级**的改变，不是功能叠加。

### 改变二：从「能跑」到「结果可被采信」

三层断言（新-2）是全部 14 项里**唯一能改变"可信度"属性**的：

1. **走偏检测**：任务期望动作序列 vs Agent 实际轨迹 → 点错地方能抓到；
2. **业务状态校验**：读页面终态与期望值比对 → 「任务成功但结果错」能被判失败（文档明确验收标准）；
3. **会话隔离校验**：并发任务状态不交叉。

配合新-1 预探索（给 Agent 页面"地图"）与新-5 隔离，形成「少走偏 → 走了能发现 → 发现得有证据」的闭环。

**形态差异**：从「AI 说成功」到「证据说成功」。这是**能不能交付给业务方**的分水岭。

### 改变三：从「能用」到「敢放开用」

| 项 | 改变的性质 |
|---|---|
| 新-6 内网/元数据拦截 | 安全边界从「事后告警」变「事前 fail-closed」 |
| 新-5 会话隔离 | 从「单任务演示」变「可并发批量」 |
| 新-3 模型分级 | 从「成本不可预测」变「按复杂度可预算」 |
| #101 配置共享 + PR 强制回归 | 从「本机能跑」变「多人可复现」 |

**形态差异**：从「我一个人演示着用」到「团队能放心接进日常流程」。

## 三、分维度提升（可测指标）

| 维度 | 现状 | 完成后 | 可测指标 |
|---|---|---|---|
| **任务成功率** | Agent 无页面先验，靠边点边猜 | 预探索注入可交互元素清单 | 走偏次数、完成步数、同任务开/关对照 |
| **结果可信度** | 人工复核 | 三层断言自动标红 | 构造反例（走偏/结果错）**必须**被抓，漏报率 0 |
| **成本可控性** | 不可预测、不可归因 | simple→flash / complex→strong | 单用例 token、两类任务花费比、日预算命中 |

| **人工衔接次数** | 生成→执行→报告靠人搬 | 编排层自动串联 | 端到端人工介入点数量 |

## 四、诚实的边界：哪些「不会」改变

避免过度承诺，以下四点不会因为 14 项完成而变化：

1. **不会变成"零人工"**：三层断言的期望值仍需人给（从「填 assert_value」变成「自然语言描述期望」，门槛降了，但不是零）。
2. **不会取代脚本化回归**：browser-use 是探索式、每次跑都可能不同；长期稳定回归仍要靠 Playwright 脚本（这正是新-7 的定位，所以它排 P3 而非砍掉）。
3. **不会自动修 bug**：只是更快、更有证据地发现。
4. **不会统一 testgen sidecar 的配置**：它用独立 venv + 独立 `.env`，与 Django `AIModelConfig` 天然隔离（#65 的"统一入口"到 sidecar 就止步）。

## 五、真正的价值跃迁点 vs 排期顺序（两者不同，需分开看）

**若只能做 3 件、拿 80% 的提升**：
1. **新-2 三层断言** —— 唯一改变「可信度」属性的项；
2. **新-5 会话隔离** —— 唯一打开「并发批量」的项；
3. **新-1 预探索** —— 成本最低、成功率提升最直接。

**但排期顺序是 P0=预探索/模型分级/内网拦截**，原因不是价值更高，而是：
- 这三项**无前置依赖、风险最低、可立即验证**；
- 新-2 依赖新-1（快照）与新-5（隔离），硬排前面会失败面过大；
- 分支保护已生效，每批必须走 PR，小批更安全。

一句话：**P0 是「先落地拿确定性收益」，跃迁点是「断言」——它在 P1，不是不重要，而是必须先铺好它的两个前置。**

## 六、一句话结论

> 14 项做完，TestHub 的变化不是「多了 9 个功能」，而是**从"能生成用例的 AI 工具"升级为"能自己跑完、自己证明跑对了、并且敢放进流水线的 AI 测试平台"**。
>
> 三个属性同时变：**可信（三层断言）、可放大（隔离+安全边界）、可预算（模型分级）**。这三条正是把 AI 测试从「演示」推进到「生产可用」的门槛。

**一个必须先修的配套动作**：新-3 模型分级要能证明省了多少钱，必须给 `AIExecutionRecord` 补 `total_tokens` / `cost` / `routed_model` 字段，否则收益只存在于日志里、无法归因到用例。这一条应并入 PR-1，不单列。

以上为评估分析，未改动任何实现代码。
