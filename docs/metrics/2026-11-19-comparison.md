### 1.2 为什么 T3 是「净 +4」而不是「+8」

E2 的 9 条里有 4 条是「限流 / 幂等 / 降级 / 超时」这类对每个入口都套一遍的泛化模板。T3 的语义维度优先级更高，把每个功能点的 4 维额度占走了，于是这 4 条被挤出、换成 4 条贴本次改动的语义维度（分页游标同步 / 翻页不重不漏 / 列表去重 / 模式分支隔离 等）。**净增 4 条，但换掉的是 4 条低信息量的模板**——这不是数量游戏，是把预算从"泛化"挪到"贴题"。

### 2.1 第 4、5 项：目标值本身基于错误预估

两项的分母都是文档编写时的**人工预估**，与 AST 实测不符：

- **影响入口「0/5 → ≥4/5」**：预估 `_record_thread_activity` 有 5 个可达入口。AST 实测其 20 个调用点**全部**落在 `chat` / `chat_resume` 两个路由函数的闭包内（max_hops 1~4 都是这 2 个），`chat` 已是本体锚点被排除 → 后端只剩 1 个入口，加上前端 2 个文件级引用方 = **3 个**。识别 3 个、覆盖 3 个，是 100%。分母从 5 变 3 不是退步，是**此前的 5 是编的**。
- **变更函数「0/1 → 1/1」**：预估当时只识得出 1 个改动函数。T5 引入 `changed_functions()` 后识别出 5 个（Python 走 AST 最内层函数、前端走顶层声明匹配），覆盖 3 个 = 60%。**这一项如实记为「未达 1/1」**—— 未覆盖的 `api/adapter.ts::threadToSession`、`api/backend.ts::listThreadsPage` 是前端薄封装，按 T4 的设计不产功能点（影响面归接口通道），是真缺口而不是统计误差。

> 这两条不做"打勾糊过去"：分母修正本身就是这批改造的价值之一——**KPI 的意义是把"我以为有 5 个入口"变成"实测 3 个入口、3 个都盖住了"**。

### 7.2 发现并修复：已作废用例被重新产出时不复活（静默不一致）

**触发链**（真实发生）：

1. X1 全量跑（同 project 30）把库中 4066 条写入，原有 321 条全部转 `obsolete`；
2. 用 E5 的收窄参数重跑恢复 → 产出 15 条，其中 2 条（`TP-5dfd4008`、`TP-cb95bbbc`，两条「回归-文件级」）内容与库中记录完全一致 → 走 `reused` 分支；
3. `reconcile_cases` 的 `reused` 分支只计数、**不改 `status`** → 这 2 条留在 `obsolete`；
4. 结果：**产物 15 条 / 库里 active 13 条**，`counts.cases=15`，但没有任何告警。报告与执行只认 `status != 'obsolete'`，于是少 2 条而看不出来。

**根因**：`store.reconcile_cases` 以 `tp_id` 为键，`reused`（内容未变）与「是否有效」被混为一谈。作废是「上次没再产出它」的结果，本次重新产出就应当复活。

**修复**（`core/store.py`）：

```python
else:
    stats["reused"] += 1
    # 内容未变 → reused，但已作废的行必须复活：不复活会让产物有 N 条、
    # 库里 active 少几条，而且完全静默——报告与执行只认 active。
    if str(old.get("status") or "") == "obsolete":
        conn.execute(
            "UPDATE cases SET status='generated', fp_id=?, fp_contract_id=?,"
            " tc_no=?, module=? WHERE id=?",
            (...),
        )
        stats["revived"] += 1
```

`case_stats` 新增 `revived` 计数（`pipeline._persist_without_db` 同步补 0），单测 `tests/test_pipeline.py::test_obsolete_case_revives_when_case_reappears` 锁定。

**修复后实测**（`gen-173f005597ea`）：

```
case_stats: {created: 0, updated: 0, reused: 15, obsolete: 4362, revived: 2}
三口径: A=15 B=15 C=15  consistent=True
```

### 7.3 运维教训

- **全量模式会覆盖同 project 的产物与库**。X1 这种"用另一套参数跑同一 project"的对照实验，必须先确认落库隔离（另开 project / `persist=false`），否则会把前一批的证据现场改成 4066 条。本次已用同步 `/api/v1/pipeline`（该分支不复用幂等任务）恢复，恢复后指标与 E5 逐项一致。
- 幂等键含 `_engine_rev()`：改代码后同一请求会真跑新任务，不会命中旧产物——这是"改完代码重启 sidecar"之外的第二道保障。

## 10. 最终结论

1. **G6 通过**：10 项判定矩阵 9 项达标、1 项按修正口径达标；三项硬指标（用例 ≥14、影响覆盖 ≥4/5、误报 0）全部达标。
2. **改造的真实价值不是"多出 13 条用例"，而是四件事**：
   - 改动不再丢（T1：私有函数改动归属到入口）；
   - 影响面有了具名入口（T2/T4：3 条，带 hunk 依据与引用方路由）；
   - 预算花在贴题的维度上（T3：换掉泛化模板）；
   - 每条用例都带可审计的命题（T5：证据 / 可观测预期 / 来源标签 + 三 KPI）。
3. **仍然诚实承认三条**：全量模式 4066 条不可用；前端薄封装 2 个函数没覆盖；三通道给不出耗时。
4. **下一步建议**（按收益排序）：
   - ① 把 `changed_func_coverage` 的分母随「所选文件范围」显式标注（避免跨组误读）；
   - ② evidence 补 hunk 行 + 被改函数名，让证据链自证；
   - ③ 前端 API 层薄封装改为「接口契约维度」产出，补上那 2 个缺口；
   - ④ 对比实验一律另开 project 或 `persist=false`，避免再出现 §7.2 的现场覆盖。
