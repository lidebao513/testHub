## 2. B1：M12 取消竞态 + M19 取消标志缓存

### 2.1 M12 根因

```
用户 cancel()  ──▶ UPDATE state=cancelled
                        │（线程池 worker 此刻才被调度）
submit._run()  ──▶ UPDATE state=running   ← 把 cancelled 覆盖掉，job 照跑到底
```

`update()` 是全字段增量更新，不带状态前置条件，**没有原子性**。单纯"先 `is_cancelled()` 再 update"仍是两步（TOCTOU 窗口仍在），只是窗口缩小。

### 2.2 M12 方案：条件更新（compare-and-set）

新增 `TaskStore.try_start(task_id) -> bool`：

```python
def try_start(self, task_id: str) -> bool:
    """pending → running 的原子迁移；已被取消/已终态返回 False。"""
    conn = connect()
    try:
        cur = conn.execute(
            "UPDATE gen_tasks SET state = ?, started_at = ?, updated_at = ? "
            "WHERE task_id = ? AND state = ?",
            (TaskState.RUNNING.value, _now(), _now(), task_id, TaskState.PENDING.value),
        )
        conn.commit()
        return cur.rowcount == 1
    finally:
        conn.close()
```

`BackgroundExecutor.submit._run()` 改为：

```python
def _run() -> None:
    if not self._store.try_start(task_id):
        # 排队期间已被取消（或任务不存在）：不执行 job，保持 cancelled 终态
        log.info("任务在启动前已被取消，跳过执行", extra=log_extra(task_id=task_id))
        return
    try:
        ...  # 原逻辑不变
```

**为什么这样最稳**：`UPDATE ... WHERE state='pending'` 在 sqlite 内是单语句原子操作（WAL 下写锁串行），不存在窗口；且顺带覆盖"任务已被删/不存在"的情形。不依赖 Redis，不需要分布式锁。

保留 `_run` 末尾原有的 `is_cancelled()` 复检（运行期取消 → 以 cancelled 覆盖 success），两条路径语义一致。

### 2.3 M19 根因与方案

`_run_generation_job._progress()` 每个阶段回调一次 `task_store.is_cancelled()`，`stage_persist` 等阶段可能高频；每次都是「建连接 + PRAGMA + SELECT」。

方案：**进程内取消标志表 + DB 回退**（保证多进程/重启后仍正确）：

```python
class TaskStore:
    def __init__(self, ...):
        self._cancelled: dict[str, bool] = {}   # task_id → 已取消

    def cancel(self, task_id: str) -> bool:
        ...  # 原逻辑
        if 置为 cancelled 成功:
            self._cancelled[task_id] = True
            self._trim_cancel_flags()
        return True

    def is_cancelled(self, task_id: str) -> bool:
        if self._cancelled.get(task_id):
            return True            # 快路径：O(1)，零 IO
        task = self.get(task_id)   # 慢路径：跨进程/重启后仍能读到 DB 真值
        hit = task is not None and task.state == TaskState.CANCELLED.value
        if hit:
            self._cancelled[task_id] = True
        return hit

    def forget(self, task_id: str) -> None:
        self._cancelled.pop(task_id, None)   # 任务终态时清理，防泄漏
```

要点：
- **快路径只在"已取消"时命中**；未取消的任务仍会查库（否则会漏掉其他进程的取消）。若要做到未取消也 O(1)，需加"本进程登记过的运行中任务"白名单，但会让跨进程取消失效——**不取此路**。
- 真正的收益：取消后的每次回调变成纯内存判断（取消场景正是回调最密集的场景）；正常路径每阶段一次 SELECT 保留，代价可忽略。
- `_trim_cancel_flags()`：超过 1000 条时按插入顺序淘汰最旧（`dict` 保序），避免长期运行内存增长。
- `BackgroundExecutor._run` 终态分支统一调用 `self._store.forget(task_id)`。

### 2.4 验收（B1）

单测（新增 `services/testgen/tests/test_task_cancel_race.py`）：

1. `try_start` 在 `cancelled` 状态返回 `False`，且 state 仍为 `cancelled`（核心回归）。
2. `submit` 一个"已 cancel 的 task_id" → job 函数**零调用**（用 `called` 计数器断言），终态 `cancelled`。
3. 正常路径：`pending → running → success`（回归）。
4. `is_cancelled` 缓存：`cancel()` 后调用 N 次，`get()` 的 mock 调用次数 ≤ 1（快路径生效）。
5. `forget()` 后内存表无该 key。

真实链路（sidecar 8910）：`POST /api/v1/generate` → 立即 `POST /api/v1/tasks/{id}/cancel` → 轮询 30s，断言终态恒为 `cancelled`、**从未出现 success**；重复 5 次（打竞态窗口）。

回滚：两处均为局部改动，`git revert` 单文件即可；无 schema 变更。

## 3. B2：M18 同步阻塞

拆成两件独立小事，可分别合并。

### 3.1 M18-b `/describe` 组间并发（优先，收益最大）

现状：6 组串行，最坏 360s；前端树加载被整段卡住。

方案：`ThreadPoolExecutor(max_workers=min(4, len(chunks)))` 并发跑各组，**返回结构与降级语义完全不变**：

```python
chunks = [need[i:i + 5] for i in range(0, len(need), 5)]
deadline = time.monotonic() + float(settings.describe_budget_seconds or 90)

def _one(chunk):
    return chunk, _describe_call_llm(chunk)   # 原 chat_with_fallback 调用体

with ThreadPoolExecutor(max_workers=min(4, len(chunks))) as pool:
    futures = {pool.submit(_one, c): c for c in chunks}
    for fut in as_completed(futures, timeout=...)   # 超预算后不再等待剩余组
```

要点：
- **单组失败仍只降级该组**（原语义）；`as_completed` 逐个合并，成功的先写缓存。
- **总预算**：新增 `settings.describe_budget_seconds`（默认 90s，`LLM_TIMEOUT` 之上）。超预算 → 未完成组按"回退展示符号名"处理，响应里 `unresolved` 如实计数，**不假装成功**。
- 并发写库：WAL + `timeout=30` 已足够；若仍抛 `database is locked`，该组降级（已有 `except`），不影响其他组。
- 结果确定性：`descriptions` 是 dict，合并顺序不影响最终内容（key 不重叠）。

新增配置项（`core/config.py`）：`describe_budget_seconds: int = 90`。

验收：
- 单测 mock `chat_with_fallback` 每次 sleep 0.2s、构造 8 组 → 断言 wall time < 1.0s（串行应 ≥1.6s），且 `descriptions` 完整 40 条。
- 单测注入一组抛异常 → 其余组仍写入，`unresolved` 只计该组。
- 真实链路：`POST /describe` 传 30 个 item，实测耗时对比（改造前/后各跑一次，记录在报告里）。

### 3.2 M18-a `/pipeline` 可选异步

现状：同步跑全链路。`/generate` 已是异步完整替代（202 + `poll_url`），但 `/pipeline` 保留给脚本/调试。

方案：**不破坏同步语义，增加可选异步开关**。

```python
class PipelineRequest(BaseModel):
    ...
    async_mode: bool = Field(default=False, alias="asyncMode")   # 显式请求异步
```

```python
@app.post("/api/v1/pipeline")
def run_pipeline(req: PipelineRequest):
    opts = build_opts_from_request(req)
    if req.async_mode:
        task = task_store.create(project_id=None, kind="pipeline",
                                 idempotency_key=_idem_key_for_generate(req),
                                 request=_redacted_request(req))
        executor.submit(task.task_id, lambda: _run_generation_job(task.task_id, opts, force_execute=opts.target_req.execute))
        return _task_accepted(task, 202)
    ...  # 原同步分支不变
```

要点：
- 默认 `False` → 现有调用方行为完全不变（零回归）。
- 异步分支复用 `/generate` 的任务模型与 `poll_url`，**不新增第二套机制**。
- 幂等键复用 `_idem_key_for_generate`（已含 `selected_paths`，M11 修复）。

验收：
- 单测：`async_mode=True` → 202、body 含 `task_id` + `poll_url`；轮询到 success。
- 单测：默认参数 → 同步返回 `{"result": ...}`（回归）。
- 真实链路：大仓（research-agent）异步跑一次，轮询进度从 0→1，前端无感（该端点前端未用）。

## 4. B3：L8 无并发上限守护线程

### 4.1 方案总览

```
run_now / 管理命令
      │
      ├─(主路径) execute_scheduled_task.delay(task_id, log_id, user_id)   → Celery worker（并发度 = worker -c）
      │
      └─(兜底：broker 不可用) _FALLBACK_POOL.submit(...)                   → 模块级 BoundedSemaphore(4)
```

**双层修复**：既接上真正的队列（生产并发上限由 worker 决定），又保证 Redis 挂了时**不再退回"每请求一条裸线程"**——这是 L8 的核心风险点。

### 4.2 新增 `apps/api_testing/tasks.py`

```python
@shared_task(bind=True)
def execute_scheduled_task(self, task_id: int, execution_log_id: int, user_id: int | None = None):
    """定时任务异步执行（对齐 app_automation/tasks.py 的 shared_task 范式）。"""
    return run_scheduled_task(task_id, execution_log_id, user_id)
```

`run_scheduled_task(...)` 是**纯函数**，抽出原 `_execute_task_async.execute()` 的完整逻辑（状态回写 + 通知），供 Celery 与兜底池共用，避免两份逻辑漂移：

- 入参由 **ORM 对象**改为 **ID**（Celery 任务参数必须可序列化；且 worker 侧要重新取对象，避免跨进程陈旧状态）。
- 内部重新 `ScheduledTask.objects.get(id=task_id)` / `TaskExecutionLog.objects.get(id=log_id)`。
- 维持原语义：`RUNNING → COMPLETED/FAILED`、`task.update_run_stats()`、`last_result`/`error_message` 回写、成功/失败通知。
- `close_old_connections()` 在 worker 内首尾各调一次（长驻 worker 防止 DB 连接失效）。

### 4.3 视图改造

```python
def _dispatch_task_execution(self, task, execution_log, user=None) -> tuple[str, str | None]:
    """提交到 Celery；broker 不可用则退回有界线程池。返回 (mode, celery_id)。"""
    try:
        async_result = execute_scheduled_task.delay(task.id, execution_log.id, user.id if user else None)
        return "celery", getattr(async_result, "id", None)
    except Exception as exc:                      # kombu OperationalError / 连接拒绝
        log.warning("Celery 不可用，退回有界线程池", extra={"err": type(exc).__name__})
        if not _FALLBACK_SEM.acquire(blocking=False):
            raise TaskQueueFull("后台执行队列已满，请稍后重试")
        def _wrapped():
            try:
                run_scheduled_task(task.id, execution_log.id, user.id if user else None)
            finally:
                _FALLBACK_SEM.release()
        _FALLBACK_POOL.submit(_wrapped)
        return "thread", None
```

- `_FALLBACK_POOL = ThreadPoolExecutor(max_workers=settings.SCHEDULED_TASK_MAX_WORKERS or 4)`，`_FALLBACK_SEM = BoundedSemaphore(same)` → **硬上限**。
- 队列满 → 视图返回 **429**（`{'error': '后台执行队列已满，请稍后重试'}`），`execution_log` 置 `FAILED` 并写明原因，**不静默丢弃**。
- `run_now` 响应体增加 `dispatch_mode`（`celery` / `thread`）与 `celery_task_id`，便于前端/排障。

### 4.4 管理命令改造

`apps/core/management/commands/run_all_scheduled_tasks.py:123` 不再 `view._execute_task_async(...)`，改调 `execute_scheduled_task.delay(...)`（同一个 dispatcher 函数），保持单一入口。

### 4.5 部署形态变化（需你确认）

- 新增常驻进程：`celery -A backend worker -l info -c 4 --pool=solo`（Windows 必须 `--pool=solo` 或 `threads`，prefork 在 Windows 不可用）。
- 启动脚本 `start_testhub.bat` 增加该 worker 的启动/停止（可选 flag）。
- **若不启动 worker**：接口仍可用，但会走兜底线程池（有上限），并打 warning —— 不会再出现"无上限裸线程"。

### 4.6 验收（B3）

单测（`apps/api_testing/tests/test_l8_task_dispatch.py`）：
1. `CELERY_TASK_ALWAYS_EAGER=True` 下，`run_now` 同步跑完、`execution_log` 终态 `COMPLETED`（回归）。
2. mock `execute_scheduled_task.delay` 抛 `OperationalError` → 走兜底池，任务仍执行完毕，响应 `dispatch_mode="thread"`。
3. 并发上限：占满 4 个坑位后再提交 → 第 5 个返回 **429**，且 `_FALLBACK_SEM` 未泄漏（结束后可再提交）。
4. 任务抛异常 → `FAILED` + `error_message` 落库（回归）。

真实链路：起 redis(6379) + worker → `run_now` → 响应 `dispatch_mode="celery"`，`celery_task_id` 非空；worker 日志出现对应任务；DB `execution_log` 终态正确。

## 6. 风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| M19 内存标志跨进程失效 | 多 worker 部署下"未取消"仍查库（**正确性不受影响**，只是没加速） | 这是有意设计：快路径只缓存"已取消" |
| `/describe` 并发触发 sqlite write lock | 个别组降级回退符号名 | WAL + timeout 30 + 组级 except；写操作本身很短 |
| `/pipeline` async_mode 误用 | 脚本拿到 202 却没轮询 → 误判失败 | 默认关闭；文档标注；响应含 `poll_url` |
| Celery worker 未起 | 全部走兜底池，吞吐受 4 限制 | 打 warning + `dispatch_mode` 暴露；启动脚本纳入 worker |
| Windows 下 worker pool | `prefork` 不可用 | 固定 `--pool=solo`（或 threads），写入启动脚本与文档 |
| 通知发送在 worker 内（SMTP 阻塞） | worker 占坑 | 沿用现状（原线程亦有此问题），后续可拆独立任务 |

- 不重构 `_send_notification`（属 H4/SSRF 与通知链路的另一议题）。

## 9. 运维收尾修复（2026-10-30 追加）

本节处理 §8.6 暴露的两个「能跑但会持续坑人」的问题：Redis 配置默认值错配、`/api/v1/` 命名空间被无障碍误用。

### 9.1 REDIS_URL 默认值错配（根因修复）

| 项 | 内容 |
|---|---|
| 现象 | worker 启动后 `AUTH <password> called without any password configured` 无限重试，任务永挂 PENDING |
| 根因 | `.env` 里**没有** `REDIS_URL`，于是回落到 settings 硬编码默认值 `redis://:1234@127.0.0.1:6379/0`（带密码），而本机 Memurai 无密码；且该默认值与 `.env.example`（无密码版）本就不一致 |
| 影响面 | 不止 worker：`CHANNEL_LAYERS`（WebSocket）、`apps/users/redis_client.py`（短信验证码）、`perf_testing`、`monitor` 心跳都共用 `REDIS_URL`。只是前者最容易暴露（长驻进程 + 重试日志） |
| 修复 | ① `.env` 补 `REDIS_URL=redis://127.0.0.1:6379/0`；② settings 默认值改为「DEBUG 时连本地无密码实例」，生产未配置则 `ImproperlyConfigured` fail-fast（不再默认带公开弱口令 `1234` 连真实实例） |
| 兼容性 | 生产部署文档 `docs/APP/PROD_DEPLOY_LINUX.md` 已显式写 `REDIS_URL=redis://:1234@...`，fail-fast 不会破坏现网；本地 `.env` 为 `DEBUG=True`，走默认分支 |

### 9.2 `/api/v1/` 命名空间归属判定

| 项 | 内容 |
|---|---|
| 现象 | 打 `POST /api/v1/users/login/` 返回 `403 未授权的代理访问`，看起来像鉴权问题，实际是路由打错 |
| 根因 | `re_path(r'^api/v1/(?P<rest>.*)$', testgen_api_proxy)` 是**全前缀通配兜底**（为转发控制台写死的 `/api/v1/` 而存在），而主平台自身 API 全部无版本前缀，于是任何 `/api/v1/xxx` 都被代理吃掉：匿名 → 403；**已登录 → 请求体（含明文密码）被原样转发给 sidecar** 并可能落进其日志 |
| 修复 | 转发前先判归属：`rest` 首段属于主平台（从 `urlpatterns` 自动推导 `/api/<seg>/`，另补 `api-testing`）→ 直接 `404` + `hint` 给出正确路径，**不转发**；属于 sidecar → 照常转发 |
| 关键坑 | sidecar 的 `/api/v1/projects` 与平台 `/api/projects/` **同名**，必须优先判为 sidecar，否则控制台项目列表会 404（已有用例锁死） |
| 附带 | 403 文案补全为「…需先登录主平台」，避免再被误读成鉴权故障 |

> **注意：本节是「缓解」，不是「根治」。** `/api/v1/` 仍被两个服务共用，判定依赖「平台段 − sidecar 段」差集。彻底解法（控制台 API 前缀可配置 + 平台专属前缀 `/testgen-api/v1`）已实施 **B1 + B2**：控制台全部请求改走 `/testgen-api/v1/*`（真实链路断言 0 泄漏），旧 `/api/v1/` 保留兼容。详见 **`docs/testgen_api_prefix_plan_2026-10-30.md`** §9；仅剩 B3（下线旧代理）待确认。
